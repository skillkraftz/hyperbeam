# hyperbeam

@RULES.md

Personal launcher for Ubuntu 26.04 (GNOME/Wayland, kitty): a "senior engineer" for many AI-assisted prototype projects. README.md has the why and how to use it; IDEAS.md the roadmap; `docs/SYSTEM.md` the one-page map; `docs/REFERENCE.md` the details (`grep -n '^## ' docs/REFERENCE.md`); `docs/decisions/` the why, one file per decision (`docs/DECISIONS.md` is the generated index).
Hotkey -> a sidebar (a Textual menu) of every project in ~/projects -> one tmux session per project with Claude Code, a shell, services (auto-started in order) and logs. The phone attaches to the same sessions over SSH (Tailscale).

## Decisions (the short list)
- Claude Code is the default agent, on `sonnet`, one session per project. Planning happens in the manager conversation (the first row); `opusplan` stays a choice in Settings.
- **Workers:** the manager, after the user said yes, starts a worker in a project (`hyperbeam work NAME PROMPT_FILE`: tmux session `claude-NAME`, a fresh Claude, no services), waits (`hyperbeam wait NAME`), reads the report, sends review feedback (`hyperbeam send NAME FILE`), ends it (`hyperbeam close NAME`). Workers always use a git worktree. hyperbeam never starts Claude work by itself.
- Manifests (`projects/<name>.toml`, in this repo, not in the projects) say how a project starts. Each project has a fixed port, set through tmux session env vars. No direnv.
- `kk` (`hyperbeam info`) lists a project's URLs; status dots show what needs attention.
- ~/.config/tmux/tmux.conf is the user's; hyperbeam adds one line, `source-file -q ~/.config/tmux/hyperbeam.conf`, a link to this repo's `hyperbeam.conf` (tmux keys and hooks).

## Rules
- **hyperbeam is installed, like any project.** The app the user runs is a clone of main at `~/.local/lib/hyperbeam` (`install.sh` makes it; `hyperbeam update` and Merge fast-forward it): never edit it, never branch in it. Manifests (`projects/<name>.toml`) are written and committed straight to main there, no branch, no PR. **Development happens in ~/projects/hyperbeam** (this folder) **on a branch**: `git fetch`, `git switch -c <branch> origin/main`; commit, push, open the PR; when merged, `git switch main && git pull`. A git worktree (`~/.cache/hyperbeam-work/<branch>`) is only for two branches at once.
- **ALL TESTING RUNS IN THE LAB.** Never run test servers (tmux, kitty, a hyperbeam menu), kills (`kill`, `pkill`, `killall`, `tmux kill-*`) or GUI apps as the user; use `hyperbeam lab run --why TEXT -- COMMAND`. This went wrong repeatedly (a `tmux kill-server` took down every session; `pkill -f "hyperbeam _menu"` killed the live tmux server, because a server's command line is the command that created it); the lab removes the possibility. Test this folder with `hyperbeam lab run --dir ~/projects/hyperbeam -- uv run --quiet --script hyperbeam ...`, or `hyperbeam hyperbeam test`. **No lab inside the lab:** `hyperbeam tool`, `shot` and `NAME test` already run in it.
- **Never run the dev folder's or a worktree's `hyperbeam` script as the user** (only `hyperbeam` on PATH): it uses the user's real state, tmux and config (PR #17: `lab status` from a worktree migrated the live state). Use the lab command above; the guard blocks the rest.
- **WINDOWS: never open, focus or leave a real window on the user's primary monitor** (DP-7). Only the far-left monitor near 0/0 (eDP-1, the laptop panel, unused) is allowed, without taking focus. GNOME/Wayland can't place windows, so default to opening none: test with an isolated tmux server and pty clients, **every test run with `WAYLAND_DISPLAY` and `DISPLAY` unset** (`env -u WAYLAND_DISPLAY -u DISPLAY`, also when the isolated tmux server starts; a fake `kitty` on PATH that only logs its arguments is fine). If a real window is truly needed: an Xwayland kitty (`HB_KITTY_ARGS="-o linux_display_server=x11 --class hbwin"`) moved with XMoveWindow to about 100,1000, X focus checked before and after, closed at once. Never test with `open_mode = "window"` unless that is the test.
- **The lab's setup is the user's** (`lab/setup.sh`, `remove.sh`, `podman-setup.sh`, the sudoers rule, the disk image at /srv/hblab). Agents never run them and never use sudo (except `sudo -n -l`). When the lab fails, check read-only (`hyperbeam lab status`, `id hblab`, `df /srv/hblab`, the end of `~/.local/share/hyperbeam/lab-runs.jsonl`), report, and never tell the user to rerun, undo or resize the lab because of an error message alone.
- **The guard** (`guard.py`, a PreToolUse hook on Bash; its rule table is the list) blocks, with a message saying what to do instead: tmux kills on the real server, `kill`/`pkill`/`killall` outside `lab run`, GUI apps with a display set, `lab reset`, `git worktree remove --force`, deleting a dirty worktree, the lab's setup scripts, any `sudo` but `sudo -n -l`, and running a dev folder's or worktree's `hyperbeam` as the user. It is textual about unquoted words: write text that mentions a blocked command with the Write tool. Never look for a way around a block: ask the user.
- Prototype for personal use: keep it simple. Verify, don't assume: check the machine before writing a fact about it.
- Never print or commit secrets (.env files, keys, tokens); say only that such a file exists. Ignored files are listed in PRIVATE.md.
- **Steno files:** `steno-YYYY-MM-DD.txt` files whose first line starts with `stenographr` can appear in any project folder: the user's dictation notes, never project files. Never commit or `git add` them (no `git add -A`/`.` while one isn't ignored), don't read them for project work.

## Where things are
- `hyperbeam`: the entry point, a small uv script that execs the parts in `hb/` in order into one namespace (so parts call each other freely, tests patch names on the script, and there are no imports inside a part: put one in `hb/config.py`). A new part goes in the list in `hyperbeam`; keep each under ~1500 lines. Each part starts with a comment saying what is in it: `config` imports, settings, helpers · `state` scan, data folders, migration, last opened · `session` start/stop sessions, status dots, drift · `workers` work/wait/close · `checks` stale docs, layouts, start and wrap-up checks · `sidebar` showing a session, the sidebar window · `lab` the lab and its digest · `verify` verify and shot · `verbs` NAME VERB, shims · `new` `hyperbeam new` · `context` align facts, context bundle · `merge` PRs and Merge · `info` kk, list, phone, scan, open, stop · `menu` the Textual menu · `cli` update/try and `main()`.
- `guard.py` the hook · `hyperbeam.conf` tmux keys and hooks · `install.sh` · `config.default.toml` · `hooks/` · `lab/` (setup scripts, rsync shell) · `tools/` (tested scripts, listed in TOOLS.md) · `tests/` · `projects/` manifests.
- Prompts: `ONBOARDING.md` and `ALIGN.md` (worker tasks the manager sends), `WORKER.md` (a worker's preamble). `manager/` is the template of `~/manager` (its CLAUDE.md is the manager's role, read from the installed copy at every start).
- State is in `~/.local/share/hyperbeam/` (per project `projects/<name>-<hash>/`, linked into each project as `.hyperbeam`); settings in `~/.config/hyperbeam/config.toml`.
- **Two hats:** hyperbeam the tool is the installed copy; hyperbeam the project is this folder; the manager is the first sidebar row (tmux session `manager`) and is not a project.

## Commands
`hyperbeam` (sidebar), `update`, `scan`, `open NAME`, `stop NAME`, `info`/`kk`, `list`, `phone`, `context`, `report`, `usage`, `refresh-prs`, `work`/`wait`/`send`/`close`/`status`, `align-facts`, `verify`, `shot`, `new NAME --cli|--web`, `lab run|status|stop|log|digest|reset`, `tool NAME|--list|--test`. **`hyperbeam NAME VERB`**: `install`, `update`, `test` (always in the lab), `version`, `help`, `restart` in every project (also `NAME VERB` and `hb VERB` in its session); Merge runs the project's `update` by itself. Details: `docs/REFERENCE.md`.
`lab run [--dir D] [--why TEXT] [--fresh] [--collect PATH] [--timeout S] [--] COMMAND` runs as the user `hblab` in a synced copy of the project (secrets and `.git` are not copied); options go before the command; bind port 0 or `$LAB_PORT_MIN`-`$LAB_PORT_MAX`. `lab reset` is the user's; agents use `lab stop`.

## Testing
`hyperbeam hyperbeam test` runs `tests/` in the lab (`uv run --with textual python3 -m unittest discover -s tests`); tools have their own `tools/<name>/test`. New tests: a throwaway set of projects (`HB_MANIFESTS`, `HB_CONFIG`, `XDG_DATA_HOME`), fake `claude`/`gh`/`wl-copy` on PATH, the menu driven through a pty read with pyte. `hyperbeam shot --cols 35` shows the real sidebar as pictures (`~/.cache/hyperbeam-shots/`): look at them after any UI change (`docs/UI.md`: 35 columns on the laptop, about 42 on the phone, mouse first).
