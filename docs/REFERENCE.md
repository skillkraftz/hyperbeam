# hyperbeam reference

The detailed description of how hyperbeam works now: moved out of CLAUDE.md so that every Claude session in this repo does not load it (CLAUDE.md is read at the
start of every session and its size is paid on every request). Read the section you need: `grep -n '^## ' docs/REFERENCE.md`, then read from that line.
CLAUDE.md keeps the rules and a map; this file keeps the details. Update the matching section here in the same PR as any change.

## Data layout, .hyperbeam, RULES.md
- **Config:** `~/.config/hyperbeam/config.toml` (settings). **Everything else is in `~/.local/share/hyperbeam/` (`DATA_DIR`, `$XDG_DATA_HOME`)**: global files (journal.json, state.json = last opened, sidebar.json/.session, menus/, outbox/, scans) and one folder per project, `projects/<name>-<6 hex of sha1 of the project's resolved absolute path>/` (`project_dir(name)`; the hash keeps two same-named projects in different folders apart). In it: `layout.json`, `status.json`, `startcheck.txt`, `claude` (blue/cyan hook state), `auto`, `prompts/`, `notes/` (human-readable notes, e.g. security briefs), `RULES.md` (symlink to the repo's). The old `~/.local/state/hyperbeam` is migrated once, automatically, at the first command (`migrate_state`: copy, check every file arrived, then remove the old folder; nothing already in the new place is overwritten; `hyperbeam _migrate-state [OLD]` runs it by hand). `kitty`/menus started before the change keep writing the old folder until restarted; the next command migrates again.
- **`.hyperbeam`** in each project is a symlink to that project's data folder, made (or remade if missing, wrong or dangling) by `ensure_link` on every Open (`open_project` and `start_session`), so `.hyperbeam/RULES.md` and `.hyperbeam/notes/` are reachable from the project. The data never lives inside the project. `.hyperbeam` is in `~/.config/git/ignore` (`ensure_git_ignore` appends the line if missing). A real file or folder named `.hyperbeam` is left alone.
- **RULES.md** (repo root) = the rules every managed project's Claude follows. Onboard runs ONBOARDING.md (manifest) and then ALIGN.md (see Align), whose proposal includes adding `@.hyperbeam/RULES.md` to the project's CLAUDE.md and flagging conflicts; nothing changes before the user approves. hyperbeam's own CLAUDE.md imports it as `@RULES.md` (it is in the repo, so it also works in worktrees). Claude Code's `@path` import: relative to the file containing it, up to 4 hops, skipped inside code spans/blocks; an import of a path outside the working directory (also a symlink whose target is outside, per the docs' rules section) asks the user to approve it once per project.
- **`hyperbeam <dir>`** (an argument containing `/` or `.`/`~` that is a folder, not a subcommand): that folder's projects for this run (`ROOT`, also `HB_PROJECTS_DIR`, which a started sidebar inherits). Without it: `projects_dir` from the config (default ~/projects).
- IDEAS.md = the queued work.

## Context: the repo is the memory
- **Decisions:** each project's CLAUDE.md describes how it works *now*, and design decisions are one file each in `docs/decisions/` (see "Decision records" below; `docs/DECISIONS.md` is the generated index). Both are updated in the same PR as the change (RULES.md says so for every project). hyperbeam's own records were seeded from the merged PRs. No MCP server; skills come later (IDEAS.md).
- **`hyperbeam context [PROJECT]`** (default `$HB_PROJECT`; the menu's **Copy context (c)** button for the selected project; `--print` prints it): one bundle for a web chat or a new Claude: header (project, path, date), RULES.md, the project's CLAUDE.md, docs/DECISIONS.md, the README, its hyperbeam manifest, recent history; a missing file says `(none yet)`. Local: clipboard (`wl-copy`), message `copied N lines`; over SSH: `~/.local/share/hyperbeam/outbox/<project>-context-<time>.txt`. Recent history (`recent_history`) is only cheap git: branch, upstream ahead/behind, `status --porcelain -uno` (the untracked scan is the slow part on big trees, so untracked files aren't counted), `log -n 20`; `GIT_OPTIONAL_LOCKS=0`, 10 s limit.
- **Model:** `claude_model` defaults to `opusplan`: Claude Code's alias that uses Opus while in plan mode and Sonnet otherwise (docs: model-config), so planning and implementation are one session per project. Plan mode: Shift+Tab cycles permission modes (default, acceptEdits, plan), or `--permission-mode plan`, or `/plan` before one prompt. Every prompt hyperbeam injects (Onboard, Fix, wrap-up, update PR, tools) starts in plan mode (`/plan ...` in a running Claude; `--permission-mode plan --allow-dangerously-skip-permissions` in a new one: bypass is allowed but not on, so approving the plan can switch to it), so Opus makes the proposal. Shown in the key sheet.

## Align (projects follow the system)
- Projects are brought in line with hyperbeam; they don't override it. A project differs from RULES.md only where its CLAUDE.md has `## Exceptions to hyperbeam rules` listing each exception and why, approved by the user.
- **ALIGN.md** (the prompt) compares the project's CLAUDE.md, README and docs against RULES.md and the real repo (`align_facts`, also `hyperbeam align-facts [PATH]`: visibility via `gh`, docs layout, decision-like docs, tests, Docker compose files, .gitignore/.env, doc lines that claim public/private), lists each difference with a proposal (change the project, or an exception with a draft reason), maps existing doc structures (e.g. dotwork's docs/product-model.md) to the system with a recommendation and asks the user to decide, then **waits for approval**, and only then works on a branch in a worktree, opens a PR and reports.
- **Onboard** (menu button/`b`, `inject_prompt`) runs ONBOARDING.md (manifest) and then ALIGN.md for configured and unconfigured projects alike: `investigate_prompt` = ONBOARDING.md + ALIGN.md + the project facts + the alignment facts.

## Review loop: report, PR badge, Merge
- **Copy report** (`hyperbeam report [PROJECT]`, default `$HB_PROJECT`; button/`p`; `--print` prints): Claude's last message of the project's session: the Claude pane = `HB_CLAUDE_PANE` of the session (else `find_claude_pane`), its conversation file via `claude_session_file` (the code behind M-y), then `last_assistant_message` = **Claude's final text answer in the turn of the user's last real prompt**. A real prompt is found from the conversation file itself (`is_human_prompt`): a user record has `origin.kind` = `human` when the user typed it, `task-notification` for a finished background task or monitor, `auto-continuation` after a usage limit; `isMeta`/`isCompactSummary` records, tool results (list content with `tool_result`) and sidechains are never prompts; a file without `origin` falls back to known tags at the start of the text (`<task-notification`, `<system-reminder`, `[SYSTEM NOTIFICATION`...). After that prompt the assistant's messages (records sharing an API message id are one message; thinking and tool calls left out) are walked in order; a **notice** (a non-human user record) marks the messages after it, and a reply to it is skipped when it came with no work since the notice (no tool call) or is under 200 characters, so a one-line answer to a leftover "Monitor ... stream ended" can't replace the report (a long answer written after real work following a notice still counts). If everything would be skipped the last text is used. Delivered by `deliver_text` like Copy context: clipboard "copied N lines", outbox over SSH ("saved N lines: path"), then the first line of what was copied in quotes so the user can see it is the right one.
- **PR badge:** for every project whose origin is on GitHub (`github_slug`: github.com or a `github-<account>` ssh alias), `open_prs` lists your open PRs (`gh pr list --author @me`, newest first), cached per project in `<project data>/prs.json` for 5 minutes (errors too); the menu refreshes in a worker thread (`poll_prs`, every 60 s, one project at a time), never in the UI thread. The row's branch text is **magenta** with an open PR; the detail line shows `PR #N: title` (the newest, `(+N more)`; a red project keeps its red reason); `kk` has a "Pull requests (yours, open)" section with URLs.
- **`hyperbeam refresh-prs [PROJECT] [NUMBER...]`** (default project `$HB_PROJECT`): fetches the project's open PRs now (`open_prs(force=True, add=NUMBERS)`) and writes the cache; the sidebar reads the cache from disk every 5 seconds (`poll_prs(False)`, disk only, no gh) so the Merge button shows within seconds, not at the next 5-minute `PR_TTL` poll. The numbers are looked up directly with `gh pr view` because `gh pr list --author` lags a few seconds behind a PR just created. It then sends SIGUSR2 to every running menu that registered `usr2` in its pid file (`nudge_menus`; an older menu would be killed by the signal), which reads the cache at once: the button shows about a second after the PR exists. `--gone N...` drops PRs just merged or closed. **Nothing has to remember to run it:** a PostToolUse hook on Bash (`prs_command` runs `hooks/pr-refresh.sh`, mark `hyperbeam-prs`, installed by `hyperbeam update` with the others) runs it in the background after any `gh pr create|merge|close`, with the new PR's number from the output's `/pull/N` and the merged/closed numbers from the command. It is a plain command, not a lab tool: it needs the user's gh login. **Hooks are idempotent:** the state hooks are recognised by `$HB_STATE/claude` (the old mark `hyperbeam/claude` no longer matched, so every update appended another set: 26 copies of each hook); one `update` collapses the duplicates.
- **gh accounts:** each call uses the token of the logged-in gh account named like the repo's owner (`gh auth token --user OWNER`, in `GH_TOKEN` for that call only, never printed). An owner without a gh login (algoviewz on this machine: neither skillkraftz nor trifactoria can see those repos) gets no badge, and merging says `no gh login for algoviewz (run: gh auth login)`.
- **Merge (m)**, shown only when the selected project has an open PR: **all of your open PRs of the project are merged, oldest first, after one confirmation** that lists them (`_merge_all`). Before each one `pr_state` fetches the PR branch and its base again (the PR before it moved main) and returns how far behind it is, the files main changed since the branch point that the PR also changed (`overlap`) and the files a merge would conflict in (`conflicts`); `None` (offline, a fork) is said out loud and merges without the check. **No overlap** (behind only in other files, e.g. a manifest committed straight to main, or not behind): merged without a question. **Overlap:** the modal for that PR says "This PR is N commits behind main, and main also changed FILES; its tests ran without those changes" with **Ask Claude to update and re-test** (Enter, the default: `update_prompt` is injected into the project's Claude with `inject_prompt`: rebase or merge main, re-run the tests in the lab, push, don't merge; needs the project running), **Merge anyway**, Cancel. **Conflict** (a dry-run `git merge-tree` of the PR branch against its base, part of `pr_state`, before anything is merged; GitHub refusing with a conflict counts too): no "Merge anyway"; Claude is asked to rebase it onto main and re-test (`update_prompt` with the conflicting files, injected into the project's Claude; if the project isn't running the summary says to open it), the run stops, and the user clicks Merge again when Claude has pushed. **The first PR that needs a look stops the run** (overlap and not merged anyway, or GitHub refuses, e.g. a conflict); the rest stay open and the summary says where it stopped ("merged #33; stopped at #34: ..."). **Stale:** a PR opened more than 7 days ago shows `[stale: Nd]` in the detail line (and in kk) and "N days old (stale)" in the list. Each merge is `gh pr merge N --merge --delete-branch` ("Base branch was modified" is retried once). Local checkout after each (`merge_pr` returns `(merged, local_ok, msgs)`), only where it is safe: when the checkout is on the default branch or on the merged branch and has no uncommitted tracked changes it goes to the default branch, `pull --ff-only`, and the merged local branch is deleted (`git branch -d`); a feature branch you are working on or uncommitted changes are left as they are, with a message. **The project's update runs once, after the last merge**: for hyperbeam itself always (`hyperbeam update` in the update popup, which restarts the menu; the installed copy updates from GitHub whatever state the dev folder is in), for other projects when the checkout was pulled. The PRs just merged are dropped from the list at once (`open_prs(gone=...)`: GitHub's PR search lags a few seconds). The badge is refreshed.
- **Lab fixes:** `lab run` options go before the command (or `--`); a misplaced `--why`/`--fresh` (and, without `--`, `--timeout/--dir/--name`) after the command is an error showing the right form; no command prints the usage with an example. pnpm in the lab: corepack 0.24 (Node 22) downloads pnpm 12 but pnpm 12 has no `bin/pnpm.cjs`, which the corepack shim runs, so it never worked (`corepack pnpm@10.4.1` does). The lab now installs pnpm once with npm into `/srv/hblab/cache/tools` and puts it first on PATH; setup.sh removes the old shim.

## Project screen and drift
- **Project screen** (`ProjectScreen`, a modal like Settings; keys `i` and `j`, the Project (j) button): `project_summary` = path, branch, port, services (up/down), open PRs (stale marker), red problems, notes, when it was onboarded and the drift note. Buttons: Onboard, Edit manifest, Copy context, Copy report, Info window (the `kk` tmux window), Mark as onboarded, **Review** (the review pass now, see Review pass), Close. A button closes the screen and the Menu runs the matching action (`run_project_action`). **Edit manifest** opens `projects/<name>.toml` in `$EDITOR` (else nvim) in a new window `manifest` of the project's tmux session and shows it on the right side (the project must be running; no manifest: says to use Onboard).
- **Drift** (no tokens): `fingerprint(path)` = the run-defining parts of `package.json` (scripts, dependency names, workspaces; not version/name), compose files (service names, images, ports), `pyproject.toml` (scripts, dependency names, optional groups), `requirements*.txt` (names), `Procfile`, `Makefile` (target names), `.env.example` (variable names), `Cargo.toml` (dependency names, bins). Versions and lockfiles are noise and skipped. Stored with the date in `<project data>/fingerprint.json` (`take_fingerprint`) when the manifest was written or changed since the last fingerprint (Onboard/Align finished: its mtime is compared), when **Mark as onboarded** is pressed, or as a silent baseline the first time a project with a manifest is checked. On Open and Refresh (`start_check`, `recheck`, also the menu's minute check) `drift_notes` compares: a difference is the quiet note `setup changed since onboarding: <file> (<parts>) (Onboard to update)`, shown in `kk`, the Project screen and the yellow status segment; never red, never the dot.

## Lab digest and tools (the system improves with use)
- **Run log -> digest** (plain script, no Claude, no tokens): `hyperbeam lab digest [--today | --since YYYY-MM-DD] [--no-tests]` reads `~/.local/share/hyperbeam/lab-runs.jsonl` and prints per project (runs, time, failed, killed = stopped by a signal, not a result), **flaky** (the same command failed, then passed, the same day; killed runs don't count), **where the time went** (the top 5 commands by total time = count x average, so six 15-minute runs rank above one 45-minute run; each shows count, average and longest), and **tool candidates** (commands and sequences in one list, biggest total first): a command repeated 3+ times (normalised by `norm_command`: a leading `cd X &&`, `2>&1`, a `| tail/head` suffix, paths, ids and long numbers stripped, so `vitest run <file>` over many files is one pattern) or a sequence of 2-3 different commands repeated 3+ times within sessions (a gap of 20 minutes starts a new one), that cost at least 30 s in total (cheap ones like `echo`/`--version` are not candidates). The tools' own test runs (`why` = `tool test: NAME`) are left out of the digest.
- **Done** (`digest_step`, first): today's digest in a few lines (`digest_summary`). With candidates (offered once per day per set of candidates: `daily_done`/`daily_mark`, `~/.local/share/hyperbeam/daily.json`) it offers **Ask Claude to propose tools**: `TOOLS_PROPOSE.md` + the digest (`tools_prompt`) are injected into the hyperbeam session's Claude (`inject_prompt`), and Done stops there (press it again after). TOOLS_PROPOSE.md: at most 3 tools, each with the work it replaces, its usage line and the time/tokens saved; skip what is not worth it; wait for approval; then build in `tools/<name>/<name>` + `tools/<name>/test`, list in TOOLS.md, open a PR.
- **Tools:** `tools/<name>/<name>` (Go, built by `build_tool` as the user when `main.go`/`go.mod` is newer than the gitignored binary; or bash/python3 for glue; runs in the lab as hblab in the current project's synced copy, `$HB_TOOLS`, `$HB_LAB=1`) and `tools/<name>/test` (exit 0 = pass; self-contained). `hyperbeam tool NAME [ARGS]` runs one in the lab (`lab run --why "tool NAME"` in the current directory's synced copy; `--dir` picks another folder); `hyperbeam tool --list` prints TOOLS.md; `hyperbeam tool --test [NAME]` runs the tests in the lab. Every `lab run` syncs `tools/` to `/srv/hblab/tools` (so `$HB_TOOLS/NAME/NAME` works too). The digest and Done run every tool's test (`tool_test_notes`) and flag a failing one as a note. **Daily check:** 20 s after the sidebar starts, once a day (`~/.local/share/hyperbeam/tools-check.json`), every tool's test runs in the lab (`daily_tool_check`); a failing tool is a red finding on the hyperbeam row (`recheck` adds `tool_check_findings`; Fix hands it to Claude), cleared by the next day's check or a passing `hyperbeam tool --test NAME`. **Usage in the digest:** per tool, runs through it (`why` = `tool NAME`), failures, and runs matching `tools/<name>/replaces` (one regex per line) that did not use it ("done by hand"). TOOLS.md is the list every agent checks first (RULES.md says so). `HB_TOOLS_SRC` points at another tools folder (tests). The guard treats `hyperbeam tool ...` like `lab run` (it runs in the lab) and allows `lab digest` from a worktree's script like `lab status|stop|log`.

## Stale docs and wrap-up notes
- **Stale docs** (no tokens): `stale_doc_items(path)` looks at `README.md` and `CLAUDE.md` of a git project: (1) commands they tell you to run that don't exist: `npm|pnpm|yarn|bun run X`, `pnpm X`/`yarn X` (not a package-manager builtin), `make X`, where X is not a `package.json` script / Makefile target (from `fingerprint`; only checked when that file exists); (2) relative paths in backticks (with a `/`, or a code/doc extension) that are not tracked, not on disk (URLs, globs, `~`, absolute paths, `<placeholders>`, `.hidden` names and generated folders like `node_modules`, `dist`, `.hyperbeam` are skipped); (3) a doc last committed 5 or more commits (`STALE_AGE_COMMITS`) that touched the run-defining files ago. `stale_doc_notes` makes one quiet note `docs may be stale: ... (Onboard runs the alignment check)` (first three findings, `+N more`), added next to the drift note in `recheck` (Refresh and the menu's minute check) and `start_check` (Open): shown in `kk`, the Project screen (`docs:` line) and the yellow status segment; never red, never the dot. `align_facts` lists all findings for ALIGN.md ("Stale docs").
- **Wrap-up notes:** every wrap-up check that finds something (`check_project`, used by Stop, `hyperbeam stop` and Done) is written by `write_wrapup_note` to `<project data>/notes/YYYY-MM-DD-wrapup.md` (`.hyperbeam/notes/` from the project; overwritten the same day): branch, git findings, steno files, secrets as file/line/pattern only, never values. It is written before the user chooses Start Claude / Stop anyway / Cancel, so it survives any choice. A clean check writes nothing. The Project screen shows `notes folder (.hyperbeam/notes): N files, latest ...`.

## Verify, shot, UI (what the user and the agent each do)
- **`hyperbeam verify [github|hooks|lab|all]`** (the user runs it; plain script, prints `PASS`/`FAIL`/`YOU` with the exact command to run): gh logins per repo owner (algoviewz has none), listing your PRs works, hooks and `model` in `~/.claude/settings.json`, the lab (ready, disk), the lab user can't read your home (`chmod 750 /home/andy` shown when it is 775), podman, and the one thing only the user can test (a real Merge, with the commands to make a throwaway PR). GitHub features beyond this are assumed to work; the lab has no GitHub credentials on purpose.
- **`hyperbeam shot [--cols 35] [--rows 40] [--phone] [--screen all|main|pr|project|settings|merge|done]`**: pictures of the real sidebar at that width. It runs `_shot-render` **in the lab** (a throwaway set of projects with long names, a PR, a working and a waiting Claude; the menu in a pty read with pyte; each screen drawn to a PNG with PIL in DejaVu Sans Mono, plus a `.txt` dump) and brings the files back with `lab run --collect` to `~/.cache/hyperbeam-shots/<time>/`. Claude reads the PNGs (Read tool). `docs/UI.md` holds the design constraints (35 columns on the laptop, ~42-46 on the phone, mouse first) and the ranked problems found at 35.
- **`lab run --collect PATH`**: after the run, rsync PATH (inside the project's lab copy, or an absolute lab path) as hblab into `~/.cache/hyperbeam-shots/<time>/` (owned by the user). The guard treats `hyperbeam shot` like `lab run`.
- **Docker in the lab:** `lab/podman-setup.sh` (sudo, once, idempotent) gives hblab rootless podman; the investigation and decision gate are in `docs/PODMAN.md` (status: waiting for the script).

## Conventions: the same verbs in every project
- **Verbs** (`VERBS` in the script): `install`, `update`, `test`, `version`, `help`, `restart`; `hyperbeam NAME VERB` (`cmd_project_verb`, dispatched in `main()` before argument parsing; a real subcommand wins on a name clash; `hyperbeam NAME` alone opens the project). Why: the user will remember "the project's name and update", not each project's steps, and prototypes that become projects lack exactly these.
- **Where a verb comes from** (`verb_command`): the manifest's `[commands]` table, then a `package.json` script or a Makefile target of that name, then a default from the folder (`detect_pm`: pnpm-lock -> pnpm, yarn.lock -> yarn, package-lock/package.json -> npm, uv.lock/pyproject -> uv, requirements.txt -> pip, Cargo.toml -> cargo). `update`, `version`, `help`, `restart` are done by hyperbeam itself unless the project defines them.
- **update** (`verb_update`): refuse on uncommitted tracked changes; fetch; check out the default branch; `pull --ff-only`; if a lockfile or manifest changed, run `install`; restart the project's service windows if its session runs (`restart_services`: `C-c`, then the manifest command again). For the hyperbeam project it runs `hyperbeam update --yes`. **test** always goes through `lab run --why "NAME test"`. **version**: package/pyproject/Cargo version + `git describe` + last commit date. **help**: each verb, what it runs, where it comes from, the manifest and data folder.
- **Sidebar:** Update (u) runs the selected project's `update` (hyperbeam's row: the update popup); the Project screen (More) has Update, Install, Test (lab), Version, Help. A verb's result is the last line of its output in the notice; the whole output is `<project data>/verb-<verb>.txt`. **After a successful Merge the project's `update` runs by itself** (hyperbeam itself: the popup), and the first successful Merge writes `~/.local/share/hyperbeam/merge-verified` so `hyperbeam verify` stops asking for a Merge test.
- **Align:** `align_facts` lists which verbs a project provides itself and which only have hyperbeam's default (`verbs_facts`); ALIGN.md proposes the smallest real addition. RULES.md says every project provides the verbs.

## Usage (the numbers claude.ai shows)
- **Why not an estimate:** the 5-hour limit is shared with claude.ai web chats, which no local file records, so any window computed from Claude Code's conversation files starts at the wrong time and counts only part of the use (the first version said "ends 3:02, 66 requests" while claude.ai said "resets Thu 1:00 AM, 83%").
- **The source:** Claude Code's status line gets `rate_limits.five_hour.used_percentage` / `resets_at` and the same for `seven_day` (Pro/Max, after the first API response of a session). `hyperbeam _hooks` (run by `hyperbeam update`, `install_statusline`) appends one marked, idempotent snippet to the user's status line script (`~/.claude/statusline-command.sh`, backup `.hyperbeam-backup`, its output unchanged; it needs the script to read its input as `$input`; with no status line configured hyperbeam adds a minimal one of its own) that writes `~/.local/share/hyperbeam/rate-limits.json` (`{at, five_hour, seven_day}`, atomic, only when the JSON has limits). It refreshes while any Claude Code runs; web-chat use since then is not in it, so a file older than 5 minutes shows `(as of 9:41pm)`, and a window past its `resets_at` shows `window reset`.
- **Shown:** the menu's title line (`5h 83% - resets Thu 1:00am`; `update available (u)` replaces it while origin/main is ahead; before any data: `5h: run any Claude prompt to refresh`), the Project screen (both limits and the conversation size) and `hyperbeam usage [--today|--week|--all]` (`usage_report`). Times are the system's local zone, 12-hour, with the weekday when it isn't today (`fmt_when`), countdown `in 2h 41m` (`fmt_left`).
- **Local numbers, honestly labelled "Claude Code only, not claude.ai":** per project requests and tokens by kind (output / new context / re-read context) and **conversation sizes** (`conversation_sizes`: what the latest request of a conversation re-read + created, read from the end of the file). The cost of a window is context size times requests, not what Claude writes.
- **Context note** (`context_note`, in `recheck`'s notes, quiet, never red): a running project whose conversation was active in the last 3 hours and re-reads at least `context_warn` tokens per request (config, default 300000) says "this conversation re-reads 836k tokens on every request: finish the task, then start a fresh Claude (Copy context carries what matters)".
- **Done never stops a Claude that is working (cyan) or waiting for you (blue)** even when its repo is git-clean: they are named and left running, only idle clean sessions are offered, and when anything is left running the session record and the sidebar window stay.

## Commands inside a session, and `hyperbeam new`
- **`NAME VERB` and `hb VERB` in a project's session:** every session hyperbeam starts has `~/.local/share/hyperbeam/bin` first on its PATH (`session_path`, written by `install_shims` on Open and `hyperbeam update`). It holds `hb` (acts on `$HB_PROJECT`; no arguments = help; outside a session it says so) and one shim per project (`dotwork help`, `dotwork update`; no arguments = help). **No shadowing:** when a real command of that name is on the PATH (stenographr is an installed CLI) no shim is made and `hb` is the way; reserved names (subcommands and the verbs) never get one; stale shims of ours are removed, other files are left alone. Only sessions are affected: other terminals keep their PATH.
- **Conforming from the first commit:** RULES.md tells every project's Claude that a CLI or app has `--version`, `help`, `update` and `install` from the start (a web app answers `/version`) and a command named after itself answering the standard verbs. **`hyperbeam new NAME [--cli|--web] [--about "..."] [--no-open]`** (`cmd_new`, `new_files`) creates `~/projects/NAME` with git, README (what / why / using it), CLAUDE.md (imports `@.hyperbeam/RULES.md`, the verbs), docs/DECISIONS.md, .gitignore, an entry point that already answers the verbs (a Python+uv CLI with `version`/`help`/`update`/`install` subcommands and tests, or a Node web app with `--version`, `--help`, `/version` and a `node --test`), the manifest (committed straight to hyperbeam's main as the rules say; a free port from 3100 for a web app) and a first commit, then Open.
- **Seeing the gap:** the Project screen and `kk` show `verbs: own: test, version; hyperbeam's: install, update, help` (`verbs_summary`); ALIGN.md compares a project's own entry point with the standard and proposes the smallest addition (for example stenographr's `update` is `uv tool install --editable ...`, not the default `uv sync`).

## Commands
`hyperbeam` is one Python script, a uv script with its dependency (textual) declared inline, symlinked to `~/.local/bin/hyperbeam`
(`ln -sfn ~/projects/hyperbeam/hyperbeam ~/.local/bin/hyperbeam`). The shebang hard-codes /home/andy/.local/bin/uv so a GNOME hotkey works

- `hyperbeam scan`: table of every git repo under ~/projects (any depth, skipping node_modules, .venv, target, dist, build...) plus top-level folders without git.
- `hyperbeam open NAME [-d]`: start the project's session if needed (no manifest: investigate prompt, see Open) and attach in this terminal (`-d`: don't attach).

  NAME defaults to $HB_PROJECT, which every session has. Sections, each skipped if it doesn't apply: Services (up/down), App (ports

  (not the current one). If nothing runs it says so and points at `list` and the menu.

## The menu
Textual app, built for a ~45-column phone screen: one list, no tabs. A row is a dot (only for running projects), the name (clipped with `…`
so the dot and port always fit) and the port right-aligned (`unset` in orange = no manifest, `-` = manifest without a port). Name: bold white if
opened within `recent_days`, else grey. Order: the `hyperbeam` row (the manager session) always first, then running, then recent, then the rest, alphabetical within each. A fresh list highlights the project the main area shows, else the hyperbeam row. Under the list one line gives the
selected project's dot reason (or nothing). Buttons (2 columns; labels without key hints below 50 columns): Open, Stop, Done, Update, **Merge** (full width, only when the selected project has an open PR of yours), **Fix** (full width, only for a red project), **More** (the Project screen: verbs, Onboard, Copy context/report, Edit manifest, Info window, Settings, Keys, Hide sidebar) and Hide (sidebar only). Keys still work: o s d u m f j (More) t (Settings) b c p h r q. Rows: dot, name, then the branch only when it is not main/master (light pink with an open PR) and the port only when set. The hyperbeam row shows `branch` (checkout is not on main) or `behind` (origin/main is ahead, fetched every 10 min) in yellow in the port column, with the long text under the list. Hidden keys:
i or j the Project screen (also the Project (j) button), r refresh, q quit (detach). Arrows move. A single click or tap on a row selects it; a double click or tap (Textual's `Click.chain >= 2`: same spot within `CLICK_CHAIN_TIME_THRESHOLD`) or Enter opens it (`ProjectList`; its handler must call `event.prevent_default()` or the base class still selects on every click).

**Dots:** green = running, services up; blue = Claude waits for the user; cyan = Claude is working; **red is rare**: only (1) a service is down/exited or failed its ready check (checked live), (2) obvious secrets in commits that are on no remote yet (`commit_secrets`, file/line/pattern only), (3) a merge/rebase/cherry-pick/revert stuck *with conflicts* (`git_red_notes`). Priority red > blue > cyan > green. Everything else the git checks find (uncommitted, unpushed, stash, behind, detached HEAD, a merge without conflicts) and a crash (saved layout not `clean`) is a quiet **note**: shown in `kk` (a Notes section), in the session's yellow status segment (`note: ...`) and, for a crash, in the hyperbeam session's `kk` until the project is opened; never the dot, never a popup; the wrap-up check at Stop/Done deals with them. Red and notes are stored in <project data>/status.json (`v: 2`, `findings` = red, `notes`), written on Open, re-run by **Refresh** and every minute by the menu, cleared on Stop. The row of a red project selected shows a **Fix (f)** button (`fix_project`). The port column: the number, `-` for a manifest without a port, orange `unset` only without a manifest (manifests are re-read every 5 s). **Row** = dot, project, branch, port (`row_text`): the dot and port are never cut, the branch is shortened first (down to 6 characters ending in `…`), then the name; the branch is read from .git/HEAD (`branch_of`: a detached HEAD shows 6 hash characters, no git `-`). The hyperbeam row is bold because the menu records it as opened; `behind` replaces its port when origin/main is ahead.

**Loud problems (red only):** `hyperbeam _entered CLIENT SESSION` runs from the tmux hooks `client-attached[91]` and `client-session-changed[91]` (hyperbeam.conf) when a client enters a hyperbeam session with red problems: setting `on_problem` (Settings screen): `"ask"` (default) shows a popup on that client (`display-popup`, the `_problem` Textual app: the problems, **Fix with Claude (f)** and **Later (l)**; it comes back on every entry until resolved); `"auto"` sends RECOVER.md to the project's Claude on entry, once per set of problems (hash in state/auto, cleared when the problems are gone). The session's status line (set per session by `tag_session`, option `@hb_alert`/`@hb_note`, kept in step by `sync_alert` whenever the status is computed) shows a red `⚠ first problem (+N): hyperbeam fix` segment, or a yellow `note: ...` one without red. `hyperbeam fix [PROJECT]` (default `$HB_PROJECT`) is the Fix button. `kk` starts with a red PROBLEMS block and the fix command (in the hyperbeam session a summary of all red projects). Note for tmux: `set-option`/`show-options -t =name` fail, use the plain session name there.

**Hooks (blue/cyan):** `hyperbeam _hooks` merges command hooks into ~/.claude/settings.json (nothing else touched, except `"model": "opusplan"`, set once so Claude defaults to it inside and outside hyperbeam: a marker `~/.local/share/hyperbeam/claude-model-set` stops later runs from resetting a manual choice; the old value is in the backup file; one backup `settings.json.hyperbeam-backup`; idempotent; replaces PR #10's older ones) that write `$HB_STATE/claude` (HB_STATE = the project's data folder, set in every session's environment; a Claude session that started before this needs a Stop and Open to get it): `waiting <reason>` on `Stop`, `Notification` (any type) and `PreToolUse` matching `AskUserQuestion|ExitPlanMode` (Claude asks a question or proposes a plan without ending its turn, which `Stop` alone misses); `working` on `UserPromptSubmit` and `PostToolUse` (so approving a permission or answering a question turns it cyan again). Plain shell, ~20 ms, a no-op without $HB_PROJECT. The state is ignored unless a process named `claude` runs in the project's Claude pane. Claude Code reads hooks at start: a Claude that was already running when the hooks were installed or changed needs a restart.
Event names and settings structure are from the Claude Code docs (code.claude.com/docs/en/hooks).

**Settings screen (t)** is a `ModalScreen`: it owns all input while open. Up/Down choose a row; Left/Right (or Enter) and the − / + buttons change it (a toggle flips, numbers and lists clamp at the ends); Esc or Close goes back. open_mode, claude_model (opusplan/sonnet/opus/haiku/fable), claude_effort (low..max), menu_width, recent_days, written to the user's config file, then the key cheat sheet. Why input used to leak (PR #10): the screen was a plain `Screen`, so (1) the App's bindings (o, s, d...) still applied on top of it (`_modal_binding_chain` stops only at a modal), and (2) its OptionList `OptionSelected` message bubbled up to the Menu's handler, which opened the next project. Now: modal, the Menu's `check_action` disables its actions whenever another screen is up, its handlers check the message's source widget, and Settings stops the events it handles. Confirm and Choice were already modals that stop their button events. **Never `return self.dismiss()`** from a handler: Textual awaits what a handler returns and a screen can't await its own dismiss (`ScreenError`, the menu crashed when Settings closed via the Close button); call it, then return. Every Claude hyperbeam starts is `claude --model <claude_model> --effort <claude_effort>` (defaults opusplan, medium).

**Layout of the hyperbeam session:** window `home` (Claude left, shell right) and window `menu` (the menu alone, full screen: on the phone it is the whole screen, no zooming). The sidebar's right client sees `home`, every other client the `menu` window (`home_target`). Windows are per session, not per client: if the phone attaches while the sidebar is looking at `hyperbeam:home`, the sidebar's right side jumps to `menu` too (it recovers on the next click).
The old layout (menu, Claude and shell in one window) is converted by `hyperbeam update`: a `menu` window is added, the old menu pane is closed, the old window becomes `home`.

**Prompt injection (`inject_prompt`, used by recover, wrap-up and onboarding):** Claude running in the target pane: one line `Read <file> and follow it.` and Enter. Otherwise `claude --continue "$(cat file)" || claude "$(cat file)"` (with the model/effort flags). Pane choice (`find_claude_pane`): the pane running claude, else the left pane of `work`, or pane 1 of the hyperbeam session. Never the menu pane (text sent there is keystrokes for the menu).

- **Open (o):** open-or-onboard. Starts the tmux session if it isn't running, then shows it according to `open_mode` (the user's config):
  `"sidebar"` (default, desktop): the menu runs in the sidebar window and Open switches the *right* client (`sidebar_client()`) to the session; over SSH or inside tmux this mode behaves like `"switch"`.
  `"switch"` switches the client that looks at the menu to it, at the laptop and over SSH (one terminal; the stack keys go back);
  `"window"` opens a new kitty window attached to the session at the laptop (over SSH it switches, there is no kitty to open).
  Local or remote is the menu client's (`client_pid`, see below), not the menu's own environment. `HB_KITTY_ARGS` adds kitty options (tests).
  If there is no manifest, or a service exits or misses its ready check, the session still opens, but its Claude pane starts
  `claude "<prompt>" --add-dir ~/projects/hyperbeam` with the investigate prompt instead of plain `claude` (it runs in the project dir,
  inside the project's session). With a manifest and no failure Claude starts plain, after the services are ready.
  The prompt is ONBOARDING.md plus project name, manifest path or "none", the tmux session, why, and the last 50 lines of each failing
  service's window; it is saved to <project data>/prompts/.
- **Stop (s):** asks first. Runs each service's `stop` command in reverse order, kills the session, then checks the project's ports are
  closed and warns if something is still listening. Without a manifest it only kills the session. Refuses to stop the session the menu itself runs in.
- **Onboard (b):** forces the same investigate path: a new session if none runs, else a new `investigate` window in the running session.
  ONBOARDING.md tells Claude to read the project, install dependencies, start and test it (Docker rule), propose the manifest and
  WAIT for approval before writing projects/<name>.toml, list project changes, not commit.
- **Refresh (r)**, **Quit (q)**: Quit detaches the client; the menu keeps running in its session. Action results stay on screen until you press Refresh.

`open` creates session `<name>` with `HB_PROJECT=<name>`, `PORT`, `HB_PORT` (if the project has a port), `HOST=0.0.0.0` and the manifest's `[env]` in its environment (no manifest: only HOST), and windows: `work` (Claude on the left 60%, a shell on the right 40%), then one window per service (its output is the log).
A service starts only after the previous one is ready. After the last one the shell pane prints real warnings (no git, no remote, uncommitted changes,
no CLAUDE.md; nothing if there are none) and then runs `kk`, and Claude starts in the left pane. Splits are percentages, so they scale when a client of another size
attaches (tested at 150 and 58 columns: at phone width the right pane gets ~9 columns, so use M-z).

## Stack, copy, mouse (hyperbeam.conf, no prefix)
- Sessions hyperbeam creates carry the tmux option `@hb`. The **stack** is the `hyperbeam` session, then those sessions by creation time.
  `M-h` goes back to the `hyperbeam` session (the menu) from anywhere (plain `switch-client`, the client that pressed it). `M-]` next, `M-[` previous, in the current client only (each client has its own position). Not in the stack: your other sessions; from one of those, `M-]` goes to the menu.
- `M-y` copies the current pane's history. **In a Claude pane** it is the whole conversation, read from Claude Code's own session file (Claude redraws its screen, so tmux's scrollback holds only the visible part): `~/.claude/projects/<cwd with every non-alphanumeric character as "-">/<session id>.jsonl`, one JSON record per line (`type` user/assistant, `message.content` a string or blocks `text`/`thinking`/`tool_use`/`tool_result`, `isSidechain`). The file is found through `~/.claude/sessions/<pid>.json`, which Claude writes for every interactive session (`sessionId`, `cwd`, and `tmux: <session>:<window>.<pane id>`, e.g. `hyperbeam:@0.%1`); without it, the newest .jsonl of the pane's directory. Output (`transcript_text`): `### You` / `### Claude` blocks, tool calls as one line `  [Bash] <command>`, no thinking, tool output, sidechains or system reminders. **In any other pane** it is the whole scrollback (`capture-pane -S -`), limited by that pane's `history-limit`: hyperbeam.conf sets 50000 (the user's tmux.conf had 5000); panes made before the setting keep the old limit. Trailing blank lines trimmed. Local client: wl-copy, message "copied N lines".
  Remote client: saved to ~/.local/share/hyperbeam/outbox/<session>-<time>.txt and the path is shown (phone delivery comes later). `HB_CLAUDE_DIR` overrides ~/.claude (tests).
- `M-s` hides or shows the sidebar (see Sidebar mode). Also `hyperbeam sidebar` and the menu's Hide (h) button.
- Mouse is on. Dragging a selection copies it to the tmux buffer, and at the laptop to the Wayland clipboard too. Shift+drag is kitty's own selection.
- `M-Left/Right/Up/Down` select the pane (wraps around), `M-z` zooms. Checked: tmux.conf binds M-Arrow only in the prefix table (resize), GNOME's Alt bindings (Tab, F4, Space, Esc, Above_Tab...) and kitty's defaults (ctrl+shift only) don't use plain Alt+Arrow or Alt+z, so nothing was moved.
  The cost: inside Claude Code's prompt, tmux now takes M-Left/M-Right, so Alt+arrow word jumps there don't work (Alt+b / Alt+f are the readline alternatives; not tested).
- The keys are shown in the Settings screen and the status-right of every hyperbeam session (set per session at creation, so other sessions keep the old bar). If you change a key, change `KEYS`/`HINT` in the script and hyperbeam.conf.
- Local or remote is decided per client, not per server: `#{client_pid}` -> that process's environment has SSH_CONNECTION/SSH_TTY, or an ancestor is sshd*, mosh-server or tailscaled. `#{client_tty}` tells nothing (both are ptys).
- wl-copy runs from the tmux server, so it needs the server's WAYLAND_DISPLAY; if the server was started over SSH it hasn't one, so the script falls back to the socket in $XDG_RUNTIME_DIR.
- Window positioning: GNOME/Wayland gives clients no way to place windows. A kitty started with `-o linux_display_server=x11` is an Xwayland window and can be moved with XMoveWindow (tested: lands on the far-left monitor, X focus unchanged). Not used by hyperbeam.

## Lab (agent testing)
Why: agents testing on the user's machine kept breaking live work. The lab is a user `hblab` (a different uid, so nothing it runs can signal the user's processes, even `kill -9 -1`) whose home `/srv/hblab` is a fixed-size ext4 disk image (`/var/lib/hyperbeam-lab.img`, `setup.sh [SIZE]` defaults to 10G, this machine's is 100G (set up 2026-11-11), on the root partition, outside the user's backed-up /home), mounted via fstab. The user runs `sudo bash lab/setup.sh [SIZE]` once (idempotent; `lab/remove.sh` undoes it; agents cannot sudo and must not run either). setup.sh: installs xvfb if missing, creates and formats the image, adds the fstab line and mounts it, creates the user, copies uv to /usr/local/bin (hblab can't read ~/.local/bin), and writes `/etc/sudoers.d/hyperbeam-lab`: `<user> ALL=(hblab) NOPASSWD: ALL` (run-as list `(hblab)`: commands as hblab only, never root; validated with visudo).
- `hyperbeam lab run [--dir DIR] [--name N] [--why TEXT] [--fresh] [--timeout S] [--] COMMAND...`: keeps **one synced copy per project** in `/srv/hblab/projects/<name>` (name = the main checkout's folder for a worktree, `lab_project_name`), made by `rsync -a --delete` run as hblab (`lab/sudo-hblab` is rsync's remote shell) from DIR (default the current directory). Excluded from the sync, so neither copied nor deleted: `.git`, `node_modules`, `.venv`, `venv`, `__pycache__`, `.next`, `target`, `.pytest_cache`, `.hyperbeam`; and never copied at all: `steno-*.txt`, `.env`, `.env.*` (not `.env.example`), `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*`. So installs (`node_modules`, `.venv`) persist and only the first run is slow; `--fresh` wipes that project's copy first. The command runs there as hblab with `env -i`: its own `TMUX_TMPDIR=/srv/hblab/tmux`, `XDG_RUNTIME_DIR`, `DISPLAY=:99` (Xvfb, started as hblab if needed, no network), no WAYLAND_DISPLAY, `HB_LAB=1`, and the caches in the lab home: `XDG_CACHE_HOME`, `npm_config_cache`, `npm_config_store_dir` (pnpm store), `PNPM_HOME`, `COREPACK_HOME`, `UV_CACHE_DIR`, `PIP_CACHE_DIR`, `PLAYWRIGHT_BROWSERS_PATH`, all under `/srv/hblab/cache` (npm, uv, pip env vars checked in the lab with `npm config get cache`, `uv cache dir`, `pip cache dir`). One argument = a shell command line, several = argv. Output streams back, the exit code is returned. `--timeout` (default 600 s) is how a test is stopped: `timeout -k 5`. **Ports:** the lab shares the machine's network (an unprivileged `unshare -n` is denied), so a lab server must bind port 0 or a port in `$LAB_PORT_MIN`-`$LAB_PORT_MAX` (39000-39999), never a project's 3100+. **Docker is not in the lab** (the docker group is root; hblab is kept out of it): Docker-based tests are listed as an exception in the project's CLAUDE.md and not run there. **GPU:** hblab joins the groups `video` and `render` (the DRI nodes); `/dev/nvidia*` are world-writable on this machine, so CUDA needs no group; the card and its 4 GB VRAM are shared with the desktop. stenographr's tests are offline (fake `nvidia-smi`), its `[gpu]` extra would download ~1.6 GB of CUDA wheels into the lab disk. setup.sh also installs rsync if missing; pnpm comes from npm into `/srv/hblab/cache/tools` on the first `lab run` (see Review loop: the old corepack shim didn't work; setup.sh removes it if it made it). Resizing the lab (remove.sh, then setup.sh with a size) is the user's own action; agents never run or suggest it (decision lab-setup-is-the-users).
- **Run log:** every `lab run` appends one JSON line to `~/.local/share/hyperbeam/lab-runs.jsonl` (written by the script as the user): `time`, `project`, `cwd`, `command`, `why`, `seconds`, `exit`, last 20 output lines (`tail`). No `--why` prints a reminder. `hyperbeam lab log [--today]` prints one line per run, totals, failures and repeated commands. It is the base for a later daily digest (IDEAS.md).
- **The lab is shared between projects; runs are isolated.** Every `lab run` has an 8-hex id and starts in its own session (`setsid -w`, so its process group is its own). While it is alive it is recorded in `/srv/hblab/runs/<id>.json` (id, project, why, command, cwd, pgid, start). Everything it starts (browsers, dev servers, even daemonised ones that leave the group) inherits `HB_RUN_ID=<id>` in its environment; that tag is how a run's processes are found (`LAB_PY`, a small python run as hblab, scanning /proc): a run is alive while some process carries its tag, records of dead runs are removed when anyone lists. Each run has its own `TMUX_TMPDIR=/srv/hblab/tmux/<id>` and `XDG_RUNTIME_DIR=/srv/hblab/rt/<id>` (so one project's `tmux kill-server` can't reach another's tmux), removed when it ends; when it ends (also on Ctrl-C/SIGTERM of `lab run`) anything it left behind is stopped. The display (Xvfb) is shared infrastructure started outside any run, never tagged, never stopped by `stop` or a plain `reset`.
- `hyperbeam lab status`: disk use, synced projects and caches with sizes, display, **active runs** (project, how long, why, id) and hblab's processes. `hyperbeam lab stop [PROJECT]` (default: the project of the current git folder, else `$HB_PROJECT`): stops only that project's active runs (SIGTERM, 3 s, SIGKILL, repeated for late children); never another project or the display. `hyperbeam lab reset [--all] [--force]`: stops your own project's runs, removes leftover per-run folders, **refuses while any other project has an active run (names them)**; `--all` also wipes synced projects and caches; `--force` kills everything hblab runs, the display included, and is **for the user only**. Runs from before this version have no record, so reset can't see them: it never kills untagged processes.
- Until setup.sh has been run every `lab` command says so and exits 2 (`lab_ready`: user missing, not mounted, or sudo rule missing, each with what to do).
- The guard blocks every `kill`, `pkill`, `killall` (also after `sudo`/`xargs`/`bash -c`) unless it is inside a `hyperbeam lab run ...` command (a `$(...)`/backtick anywhere in the line disables that exemption). It is textual: a script that calls `os.kill` isn't seen, so run such scripts through the lab.
- The guard also blocks `hyperbeam lab reset` (any form: agents use `lab stop`), `git worktree remove --force/-f`, and `rm -r` of a git worktree folder (or of `~/.cache/hyperbeam-work`) that has uncommitted or untracked files (`lab-reset`, `worktree-force-remove`, `rm-dirty-worktree`; the last one runs `git status` in the folder). `lab status|stop|log` are allowed from a worktree's script (they never touch state). The guard also blocks running a `hyperbeam` script that sits in a worktree (a folder under `~/.cache/hyperbeam-work/` or with a `.git` file) outside `hyperbeam lab run`: directly, by `cd` + `./hyperbeam`, or through python/bash/uv/timeout/env/sudo (`worktree-script-outside-lab`; it uses the hook's `cwd`; a bare mention such as `git add hyperbeam` or `py_compile hyperbeam` is allowed). Only `hyperbeam lab run ...` itself may start from a worktree.
- **Docker/podman in the lab:** `lab run` writes `podman` and `docker` shims into hblab's `~/.local/bin` (`lab_ensure_shims`; runtime dir `/tmp/hblab-podman`, a `podman system service` socket for `docker`/`docker compose`); single containers and host-network compose work, compose's own networks do not yet; details and results in `docs/PODMAN.md`.
- `hyperbeam context --size` / `--full`, `verify merge`, `ignore_owners` (user config: owners hyperbeam ignores): see the commands above and `config.default.toml`.
- Until the lab exists on a machine, tests fall back to the older way (isolated tmux server via TMUX_TMPDIR, pty clients, DISPLAY unset), but nothing destructive.

## Guard (PreToolUse hook on Bash)
Why: agents inside a hyperbeam session have `$TMUX`, so a bare `tmux ...` talks to the user's REAL tmux server. A `tmux kill-server` from a Claude working on stenographr once took down hyperbeam and every project session. CLAUDE.md text didn't stop it; this does.
- **Mechanism** (Claude Code hooks docs): a `PreToolUse` hook with matcher `Bash` gets `{"tool_name": "Bash", "tool_input": {"command": ...}}` on stdin. **Exit 2 with a message on stderr blocks the call and the message goes to Claude**; exit 0 with no output allows it (JSON `hookSpecificOutput.permissionDecision: "deny"` is the other way). Tested with a real `claude -p --permission-mode bypassPermissions`: still blocked, message delivered.
- **Lab rules** (decision lab-setup-is-the-users): blocks a lab command inside `hyperbeam lab run` (`tool`, `lab`, `shot`, `NAME test`: the lab inside the lab fails with "sudo may not run commands as hblab", because hblab has no sudo; `lab_ready` refuses it too when `HB_LAB=1`), running `lab/setup.sh`, `remove.sh` or `podman-setup.sh` (reading them is fine), and any `sudo` except `sudo -n -l`. The lab's own error messages state facts only and never tell anyone to run the setup.
- **Which server a `tmux` reaches:** the socket in `$TMUX` (the real server) unless `-L <name>` or `-S <path>` names another. Verified on an isolated server: from inside a pane, `TMUX_TMPDIR=...` and `env -u TMUX` still reached that same server; only `-L`/`-S` reached another. So the guard accepts only `-L`/`-S` naming another socket (a `-L` equal to the basename of the `$TMUX` socket, or `-S` the same path, is the real one).
- **Rules** (`RULES` in `guard.py`, the whole list is there): (1) tmux kill-server/-session/-window/-pane (and killw/killp) not aimed at another socket; (2) pkill/killall/kill aimed at tmux or kitty, and any `pkill -f` / `kill $(pgrep -f ...)` / `pgrep -f | xargs kill` (a tmux server's command line is the command that created it, e.g. `hyperbeam _menu; ...`, so `pkill -f "hyperbeam _menu"` killed the live server on 2026-11-11) (by name, `$(pgrep|pidof tmux|kitty)`, or a pid whose /proc comm is tmux/kitty; a pattern naming `tmux -L`/`-S` is allowed); (3) a GUI app (kitty, terminals, browsers, editors...) started while WAYLAND_DISPLAY or DISPLAY is set in the environment, unless the command unsets both (`env -u WAYLAND_DISPLAY -u DISPLAY ...`). Everything else is allowed. It is textual, so a command that merely mentions `tmux kill-server` (e.g. in `echo`) is blocked too; that is accepted.
- **Install:** `hyperbeam _hooks` merges it into `~/.claude/settings.json` with the state hooks (idempotent, other keys untouched). The hook command runs `exit 0` at once without `$HB_PROJECT`, else `/usr/bin/python3 <repo>/guard.py` (stdlib only, ~17 ms). Run `_hooks` from the live checkout (`~/projects/hyperbeam`), not a worktree, since the settings point at that path. Claude Code reads hooks at start: restart Claude sessions.
- hyperbeam's own tmux calls are not affected: hooks see only Claude's tool calls. Test a rule by feeding sample JSON to `guard.py`, never by running the command.

## HB_CLAUDE_PANE (for tools running in a pane, e.g. stenographr)
Every project session and the hyperbeam session has `HB_CLAUDE_PANE` = the tmux pane id (`%12`) of that session's Claude pane (the left pane of `work`, or `home`'s Claude; for a restored layout the pane with role `claude`). Panes created in the session after it was set (new windows, splits: where stenographr runs) have it in their environment; the session's own shell pane and Claude pane get it exported when they are made (`publish_claude_pane`), and `tmux show-environment -t SESSION HB_CLAUDE_PANE` always answers. It is set at session creation, after a layout restore, and re-checked by `_save` (every detach, session switch, 5 minutes) and `hyperbeam update`: if the pane it names no longer exists it is re-derived (`refresh_claude_pane`). Use: `tmux send-keys -t "$HB_CLAUDE_PANE" -l "text"`. A tool in the pane should not guess which pane is Claude.

## Sidebar mode (desktop)
One kitty OS window, two kitty splits: the menu on the left (`menu_width` columns), `tmux attach` on the right. A double click or Enter in the menu switches the right client to the session (creating it if needed); the sidebar stays. M-[ M-] M-h act on the client that pressed them, i.e. the right one.
- **One window:** the session file must not start with `new_os_window`: kitty's parser starts with an implicit first OS window, and a leading `new_os_window` closes that one off as an *empty* shell window (`finalize_session` gives every window-less tab a default shell) and opens a second. The GNOME hotkey command is plain `/home/andy/.local/bin/hyperbeam`. Checked with kitty's own `create_sessions`: 1 OS window, 1 tab, 2 windows.
- **Hide / show** (`sidebar_toggle`, `M-s` in tmux.conf on the right client, `hyperbeam sidebar`, the menu's Hide (h)): `kitten @ --to unix:$XDG_RUNTIME_DIR/hyperbeam-sidebar` `goto-layout stack` (after `focus-window --match title:^main$`, so the visible one is the tmux side, full width) and back with `goto-layout splits`. The layout is read from `kitten @ ls` (no state file). Nothing is closed, the menu keeps running. The sidebar is started with `-o enabled_layouts=splits,stack`. Only works on a sidebar started by this version (it needs the socket).
- **Half-open sidebar** (`launch_sidebar`): if the window is open (kitty pid alive) but one half is missing (no tmux client on the recorded right tty, or no sidebar menu pid; a window younger than 8 s and a menu between restarts get grace), the hotkey closes it (`close_sidebar`: `kitten @ close-tab --match all`, else SIGTERM to that kitty, its cmdline checked) and opens a new one, saying so; it says "already open" only for a whole window. **Done** (all clean, sessions stopped, record cleared) in the sidebar closes the whole window (a detached `hyperbeam _close-sidebar`, since the menu is inside it); the tmux sessions are not touched.
- **Launch** (`launch_sidebar`): creates the hyperbeam session, writes `~/.local/share/hyperbeam/sidebar.session` and runs `kitty --class hyperbeam-sidebar --title hyperbeam --session <file>`. A second call says it is already open (pid in sidebar.json). The session file: `os_window_class`, `os_window_size 170c 48c`, `layout splits`, `launch --title menu --env HB_SIDEBAR=1 sh -c '<menu loop>'`, `focus`, `launch --location=vsplit --bias=N --title main hyperbeam _right`. kitty's own parser accepts it (checked with `kitty +runpy` and `kitty.session.parse_session`: 170x48 cells, class, splits, two windows). The left width: `--bias` is the percentage the new right window takes, computed from `menu_width` (73 for 45 of 170); the exact column count is a hand test. The sidebar is started with `-o allow_remote_control=socket-only --listen-on unix:$XDG_RUNTIME_DIR/hyperbeam-sidebar` (command line only, so only this kitty is remote-controllable; kitty puts `KITTY_LISTEN_ON` in the windows' environment). The menu then sets its own width in columns: `Menu.fit_width` measures its width and runs `kitten @ resize-window --self --axis horizontal --increment <wanted - width>` (up to 4 tries, since the split moves by a computed number of cells); on start and whenever `menu_width` changes in Settings, so it applies at once. `--bias` at launch is only a percentage of the real window (the 170 columns of `os_window_size` are a request, a maximized window is wider), which is why `menu_width` alone never gave the wanted column count. Without `KITTY_LISTEN_ON` (a sidebar opened before this version) the change applies at the next launch and the Settings screen says so.
- **Which client is the right side** (`cmd_right`): `hyperbeam _right` records `os.ttyname(0)` in sidebar.json, then `exec`s `tmux attach -t =hyperbeam`. A client's `#{client_tty}` is that same tty, so `sidebar_client()` = the recorded tty if `list-clients` still lists it, and the menu does `switch-client -c <tty>`. Nothing is guessed from activity. Menus not started by the sidebar (`HB_SIDEBAR` unset) keep using `menu_client()` (the client looking at the menu session).
- **Stop and the right side:** stopping a project moves every tmux client looking at it (the right side) to `hyperbeam:home` *before* the session is killed, so the right split never closes; project sessions also get `detach-on-destroy off` as a safety net for any other way they end. If the right split is gone anyway (closed by hand), `show_session` opens it again with `kitten @ launch --location=vsplit --title main hyperbeam _right` and then switches. Decision: manager-session-is-home.
- **Width on resize:** `Menu.on_resize` calls `fit_width` again (debounced 0.5 s) when the width differs from `menu_width`, so resizing the window keeps the sidebar's columns; `fit_width` does nothing while the layout is `stack` (hidden).
- **The menu runs outside tmux** in the left split: Textual's mouse and double-click (`Click.chain`) work on any xterm-mouse terminal; tested in a pty without tmux. Quit (q) exits the menu with code 0, which ends the loop and closes that split; any other exit (a restart signal, a crash) restarts it after a second.
- **Info window** (a button of the Project screen) in the sidebar opens the info window in the hyperbeam session and shows it on the right client. **Update (u)** runs `hyperbeam update` in a tmux popup on the right client (the update restarts the menu, so it can't run in it).
- Not for the phone: over SSH (`SSH_CONNECTION`/`SSH_TTY`), inside tmux, or without a screen, `hyperbeam` attaches as before.

## Update and try
`hyperbeam update` (also the menu's Update button): refuses if ~/projects/hyperbeam has uncommitted tracked changes; `git fetch`, check out `main` (or the branch for `try`), fast-forward to `origin/<branch>`, print `branch old -> branch new` and the new commits; then the *new* script's `_update-finish`: `_hooks` (state hooks + guard), reload hyperbeam.conf into tmux and refresh the status hints, restart the menus without touching a project session (sidebar menus: SIGUSR1 to the pids in `~/.local/share/hyperbeam/menus/` whose `home` is this checkout, they exit 75 and their loop restarts them; the in-tmux menu pane is respawned; the old layout is converted), then list every Claude pane in a hyperbeam session (idle = blue, working, unknown) and offer to restart the idle ones with `claude --continue` (`respawn-pane`, then the command typed; `--yes` skips the question; the pane the update itself runs in is never touched; working ones are left to the user). `hyperbeam try BRANCH` is the same with that branch checked out; `update` returns to main. Tests use `HB_SETTINGS` (instead of ~/.claude/settings.json) on a scratch clone, never the live repo.

## Beam in: layouts and the start check
- **Layouts** are saved to <project data>/layout.json: per window its name and tmux `#{window_layout}`, per pane its cwd, role (`claude`, `shell`, `service:<name>`, `other`) and, for `other`, the program running in it, the active window and pane, a time and `clean`. Saved: on Stop (with `clean: true`), when a client detaches or its terminal goes away or it switches session (tmux hooks `client-detached[90]` and `client-session-changed[90]` in hyperbeam.conf run `hyperbeam _save`, which saves every hyperbeam session because the hook has no session name left to give), every 5 minutes while the menu runs, and once when a session starts. `select-layout` with a saved string works on a different window size (tmux rescales when a client attaches) but is silently ignored if the pane count differs, so panes are created first.
- **Open** on a project that isn't running but has a saved layout brings it back without asking (decision layouts-come-back-whole): windows, panes, cwds, layouts and the active pane are recreated; services restart from the manifest in order; Claude panes run `claude --continue` (the most recent conversation in that directory; falls back to a fresh `claude` if there is none), only the first per directory; a pane that was running a program (`prog`, the command line of the shell's first child process, e.g. `nvim notes.md`, `tail -f log`; not a shell, Claude, `sudo` or tmux) gets that command typed again (`restart_programs`; Ctrl-C leaves a shell), other panes get a shell. The **hyperbeam session** is saved like the projects (its `home` windows; `menu` is always rebuilt) and `ensure_menu` rebuilds it the same way after a reboot; no saved layout gives the default `home` (Claude left, shell right). A saved layout is only the panes: the choice of continuing the last Claude conversation or starting a fresh one is a separate step (planned, docs/SYSTEM.md).
- **Start check** (`start_check`, built on `git_problems`, which the wrap-up check will reuse; `hyperbeam _check PATH [--fetch]` prints it): uncommitted changes, unpushed commits (or commits on no remote), stashes, detached HEAD, merge/rebase/cherry-pick/revert in progress, behind the upstream (after a `git fetch` with a 6 s limit, no prompts, ssh ConnectTimeout 3, failure ignored), and "not stopped cleanly" (a saved layout with `clean: false` and no running session: crash, reboot, killed session). steno files are left out of the counts; one git could commit (tracked, or untracked and not ignored) is reported as its own warning. The results print above `kk` in the shell pane. Only *red* findings (see Dots: conflicts, secrets in commits) count as problems; everything else is a note printed in the shell pane and shown in kk. If a red problem was found (and the project has a manifest and it isn't Onboard) it asks "Start Claude to sort it out?": yes starts Claude with RECOVER.md plus the findings (with `--continue` if the layout was restored). RECOVER.md: diagnose read-only, propose, wait for approval, never commit steno files. No Claude unless the user says yes.

## Beam out: session record and wrap-up check
- **Session record** `~/.local/share/hyperbeam/journal.json`: `started`, `menu_started`, and the projects opened or switched to (`touch_opened`, and the `client-session-changed` hook via `hyperbeam _save <session>`). Survives a menu restart; cleared only by a completed Done for now.
- **Wrap-up check** (`wrapup_check`, reuses `git_problems(..., behind=False)`; `hyperbeam _wrapup PATH [--since TS]` prints it): uncommitted/unpushed work, stashes, detached HEAD, merge/rebase; steno files tracked or not ignored; obvious secrets in commits since the record started, staged and unstaged changes, untracked files, and secret-looking tracked file names (.env, id_*, *.pem, *.key, credentials.*; `.env.example` etc. are safe). Patterns: private-key headers, AWS/GitHub/Slack/Stripe-live/Google/Anthropic-OpenAI keys, URLs with a password (not localhost), literal password/secret/token/api_key assignments (skipped in test/fixture dirs, placeholders and low-variety values). Output is file, line, pattern name (and commit), never a value. Real repos: 0 hits on 21 repos' tracked files after the test-dir exemption (1 before).
- **Stop** (menu or `hyperbeam stop`, `--force` skips) runs it first: clean, confirm and stop; not clean, choose Start Claude to wrap up (WRAPUP.md plus findings, in the project's Claude pane: typed as a one-line pointer if Claude runs there, else `claude "$(cat file)"`), Stop anyway, or Cancel.
- **Done for now (d)** checks every recorded project: all clean, offers to stop their sessions and clears the record; otherwise offers Claude in the hyperbeam session's Claude pane with all findings; press Done again when finished.

## Manifest format
`projects/<name>.toml` in this repo (not in the project). Written by Claude through Onboard (there is no heuristic drafting). `port` is optional: a project with nothing to serve has none, and then no PORT/HB_PORT is set. Ports start at 3100 and never repeat across manifests.

```toml
path = "~/projects/plantlab"
port = 3101

[[service]]                # ordered; each waits for the previous one to be ready
name = "db"                # tmux window name
cmd = "docker compose up"  # run in the project dir; sees $PORT and $HB_PORT
ready_port = 54322         # wait until this TCP port opens. Default: the project's port. false = don't wait
stop = "docker compose down"   # optional; Stop runs these in reverse order before killing the session

[[service]]
name = "dev"
cmd = "pnpm dev"           # ready_port defaults to port = 3101
ready_delay = 5            # optional: sleep N seconds first (alone, it replaces the port check)
ready_timeout = 60         # optional: give up waiting after N seconds (default 120)

[env]                      # optional: extra session env, overrides the defaults (HOST=0.0.0.0)
SOME_VAR = "value"

[links]                    # optional: extras `kk` cannot discover; name = url
docs = "https://example.com/docs"
```
A service that exits before its port opens is reported as a warning and the next one still starts.

Docker rule: app dev servers run on the host in a tmux window; backing services (databases, Supabase, Caddy...) run through docker compose;
containerize the app itself only if the project specifically needs it.

## Decision records
- **One file per decision:** `docs/decisions/YYYY-MM-DD-slug.md`. Front matter between `---` lines: `id` (must be the file name), `status` (`implemented` | `superseded`), `topic` (one word; `unsorted` until the review pass sorts it), `prs` (`[40]`), and optionally `supersedes: [ids]`, `collapsed_into: [ids]`, `code: path:function`. Then `# Title` and the Decision / Why / Rejected bullets.
- **Superseding:** a decision that replaces earlier ones lists them in `supersedes`; each of those becomes `status: superseded` and says what absorbed it with `collapsed_into` (a decision) and/or `code` (the code that now embodies it). The implemented set is what is currently true; the superseded ones stay as the way back.
- **Why files:** two PRs never touch the same file (every PR used to add an entry at the top of one file, which conflicted). `docs/DECISIONS.md` is generated from the records (`hyperbeam tool decisions index > docs/DECISIONS.md`) and is only regenerated by the review pass, never by a feature PR.
- **`hyperbeam tool decisions`** (Go, `tools/decisions/`): `list [--topic T]` (implemented only), `check` (id = file name, status, topic, title, every `supersedes`/`collapsed_into` target exists, a superseded decision names what it collapsed into, nothing superseded is still implemented, no cycles), `index`. `--dir DIR` picks the project folder (default: the current directory). Test: `tools/decisions/test`.

## Review pass
- **What:** after `review_after` (default 5, a setting, shown as `review at` in Settings) PRs merged since the project's last review, a review is offered. Claude, in plan mode, reads the whole batch (REVIEW.md + `review_facts`: the merged PRs with their files, decision records added, the size of the change, IDEAS.md, the last record), proposes **one** cleanup PR (duplication, hacks, missing tests, docs that no longer match, decisions that replaced each other, IDEAS items to close) and waits for approval. After approval it does it, writes the review record, regenerates the decisions index, opens `Review: PRs #A to #B`, and says "Review done."
- **The record:** `docs/reviews/YYYY-MM-DD.md`, front matter `through` (the last merge commit it covered), `prs`, `refactored`, `docs_updated`, `decisions_superseded`. The newest one answers "when was the last review and what did it cover". A project with no record counts from its **onboarding** instead (`review_baseline`: the last commit of the default branch at the date in `fingerprint.json`, the root commit if every commit is newer; the record-like dict has `baseline: True`, and the notes say `since onboarding`); the first review writes `docs/reviews/` and from then on the record is used. A project never onboarded (no fingerprint, no record) is in no loop and nothing is counted. REVIEW.md has a paragraph for this first review.
- **Counting:** `reviews_due(path, name)` = `git rev-list --merges --first-parent --count <through>..origin/<default branch>`. It is a quiet note on the project row ("3 of 5 PRs since the last review", `review_notes`, via `recheck` and `start_check`, so **Open** prints it in the shell pane and kk shows it: "review due: 5 PRs merged since onboarding (2026-11-12); Open and Done offer it (Project, Review)"), a line in `hyperbeam context` ("Last review ..., 3 PRs merged since", `review_line`, so a new session knows how much room is left), and the Done offer.
- **Review button** (Project screen, `action_review`): starts the review for the selected project at once (`start_review`), whatever the count; refused with a message when nothing merged since or the project was never onboarded. The running Claude is replaced (Previous Claude brings it back); not while it is working.
- **Done:** `review_step` runs after the lab digest step: for each project worked on today with `review_after` or more merges since its last review (offered once a day per project, `daily_done`/`daily_mark` with the key `review:<project>`) it asks "Ask Claude to review (r) / Later (l)". Asking runs `start_review`: a **fresh Claude in plan mode replaces the project's Claude in the same pane** (`swap_claude`: respawn the pane, `claude --permission-mode plan` with the prompt, no `--continue`; refused while Claude is working), so with opusplan Opus plans and nothing depends on the old session's mode. The conversation it replaced is remembered (`previous-claude` in the project data folder) and comes back with **Previous Claude** in the Project screen or `hyperbeam back` (`back_claude`: `claude --resume <id>`). The offer is used up only when the review started; Done stops there and says to press it again after "Review done." Done never blocks stopping.
- **The snapshot:** the fresh Claude has no chat history, so the prompt carries `review_snapshot`: CLAUDE.md, the decisions index, IDEAS.md, the `Last review` line, the recent history and what the previous session last said (`report_text`, 2000 characters), each part cut at 12,000 characters (about 6k tokens for hyperbeam; the start message shows the size). README.md and docs/REFERENCE.md are for it to read on demand.
- **`hyperbeam review [PROJECT] [--since COMMIT] [--print]`:** the same by hand (default project `$HB_PROJECT`). `--since` is only needed for a project that was never onboarded and has no record; `--print` prints the prompt instead of swapping. **`hyperbeam back [PROJECT]`** resumes the conversation that was set aside.
- **Always Opus planning:** every prompt hyperbeam writes starts with a plan-first line (`PLAN_FIRST`: call EnterPlanMode if plan mode isn't active). The guard blocks `hyperbeam review ... --print` when the hook input's `permission_mode` is present and not `plan` (`reviews_outside_plan`; ignored when Claude doesn't send it), with a message to call EnterPlanMode or run the command without `--print`.
