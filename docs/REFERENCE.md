# hyperbeam reference

How hyperbeam works now, by topic. Not in CLAUDE.md so that every session does not pay for it: `grep -n '^## ' docs/REFERENCE.md`, then read the section you need.
One place per fact: CLAUDE.md keeps the rules and a map, `docs/SYSTEM.md` the picture, this file the details, `docs/decisions/` the why. Update the matching section in the same PR as a change.

## Install, data and settings
- **Installed app:** `bash install.sh` (idempotent, from any checkout) clones origin into `~/.local/lib/hyperbeam` (or fast-forwards it to `origin/main`), links `~/.local/bin/hyperbeam`, `~/.local/bin/kk` and `~/.config/tmux/hyperbeam.conf` to it, and runs `hyperbeam _hooks` so the guard in `~/.claude/settings.json` points at the installed `guard.py`. `HERE` (the script's real folder) is that copy: prompts, manifests (`projects/`), tools, lab scripts, RULES.md, hyperbeam.conf, guard.py. `update` and Merge fast-forward it; manifests are committed and pushed to its main. Test overrides: `HB_LIB`, `HB_BIN`, `HB_TMUXCONF`, `HB_ORIGIN`, `HB_SETTINGS`.
- **The project "hyperbeam"** is `~/projects/hyperbeam` (the sidebar row, its state folder); development there is on a branch from `origin/main`. `known_path(name)` is the one way to find any project's folder: manifest `path`, else `~/projects/<name>` (nested names use `_` for `/`), else a scan.
- **Settings:** `~/.config/hyperbeam/config.toml` (`HB_CONFIG` in tests) over the repo's `config.default.toml`; the Settings screen writes only the user file. Keys: `open_mode` (`sidebar` | `switch` | `window`), `claude_model` (default `sonnet`; `opusplan` makes every prompt hyperbeam injects start in plan mode), `manager_model` (`opus`), `claude_effort` (`medium`), `claude_permissions` (`skip` = every Claude hyperbeam starts runs with `--dangerously-skip-permissions`, the guard still runs; `ask`), `menu_width` (45), `recent_days` (7), `context_warn` (300000 tokens), `accounts` (GitHub accounts that count as "mine"), `ignore_owners` (owners with no badge, no Merge), `projects_dir` (`~/projects`). `hyperbeam DIR` uses another folder's projects for one run (`HB_PROJECTS_DIR`). A `migrate_config` from the repo's old `config.toml` and `migrate_state` from `~/.local/state/hyperbeam` still run (both date from 2026-11-10/11).
- **Data:** everything else is in `~/.local/share/hyperbeam/` (`$XDG_DATA_HOME`): global files (`journal.json`, `state.json` = last opened, `rate-limits.json`, `lab-runs.jsonl`, `tools-check.json`, `sidebar.json`, `sidebar.session`, `menus/` pid files, `outbox/`) and one folder per project, `projects/<name>-<6 hex of sha1 of its path>/` (`project_dir(name)`): `layout.json`, `status.json`, `claude` (hook state), `fingerprint.json`, `prs.json`, `prompts/`, `reports/`, `notes/`, `RULES.md` (link to the repo's).
- **`.hyperbeam`** in each project is a symlink to its data folder, remade on every Open (`ensure_link`), so `.hyperbeam/RULES.md` and `.hyperbeam/notes/` are reachable from the project; it is in `~/.config/git/ignore`. A real file named `.hyperbeam` is left alone.
- **RULES.md** is what every managed project follows; the aligned project's CLAUDE.md imports `@.hyperbeam/RULES.md`, hyperbeam's own imports `@RULES.md`. A project differs only in its CLAUDE.md `## Exceptions to hyperbeam rules`, approved by the user.
- **Environment:** `uv run --script` leaks VIRTUAL_ENV, UV and a uv `bin` into PATH; the script strips them and `start_session` removes them from a running tmux server's global environment.

## Commands
`hyperbeam` is a uv script (textual declared inline) that execs the parts in `hb/` into one namespace; the GNOME hotkey runs `/home/andy/.local/bin/hyperbeam`.
- `hyperbeam`: on the desktop (`open_mode = "sidebar"`, not over SSH or inside tmux, a screen available) opens the sidebar window; otherwise attaches to tmux session `manager` on its `menu` window.
- `update` / `try BRANCH`: see Update. `scan`: every git repo under ~/projects. `open NAME [-d]`: start and attach (`-d`: don't attach). `stop NAME [--force]`: Stop without the menu.
- `info [NAME]` = `kk`: the project's URLs, one per line, discovered: Services (up/down), App (ports its session listens on), Tailscale, Docker (containers by compose `working_dir`), Supabase (URL values only, never keys), Vercel, Git (web URL), `.env` URL variables (passwords masked unless local), Extra (`[links]`), your open PRs (stale ones marked), and a PROBLEMS block first when something is red. NAME defaults to `$HB_PROJECT`.
- `list`: numbered running sessions, most recent first, with port, up/down and Tailscale URL; a number switches or attaches. `phone`: the URL list, then attach to the most recently used session.
- `context [NAME] [--print|--size|--full]`: a bundle for a web chat or a fresh Claude (RULES.md, CLAUDE.md, docs/DECISIONS.md, README, manifest, cheap git history). Clipboard (`wl-copy`) locally, `outbox/` over SSH. `copy-last [NAME] [--print]`: Claude's last answer (below; it was `report`, which now only says so). `reports [--since DATE] [--since-refactor] [NAME...]`: one row per worker report (date, project, task, branch, PR, commits, tokens in+cache creation / cache reads / output, API calls, active minutes from the transcript with gaps over 10 min removed, lab seconds from `lab-runs.jsonl` of that project inside the run's started-finished window) and a total; `--since-refactor` = after the last report whose task's first line matches refactor|cleanup|audit. `usage [--today|--week|--all]`. `align-facts [PATH]`: facts for ALIGN.md (visibility, docs layout, tests, compose files, `.env`, stale docs, which verbs the project provides itself).
- `work`, `wait`, `send`, `close`, `status`: workers. `tidy [NAME] [--yes]`: merged branches and worktrees. `lab ...`, `tool ...`, `verify`, `shot`: below. `new NAME --cli|--web`: below. `refresh-prs`: below.
- Internal (`_hooks`, `_save`, `_check`, `_wrapup`, `_entered`, `_right`, `_menu`, `_worker-report`, `_close-sidebar`...): called by tmux hooks, Claude hooks and the menu.

## Verbs, shims and `hyperbeam new`
- **Verbs** (`VERBS`): `install`, `update`, `test`, `version`, `help`, `restart`; `hyperbeam NAME VERB` (a real subcommand wins on a name clash; `hyperbeam NAME` opens). `verb_command` looks in the manifest's `[commands]`, then a `package.json` script or Makefile target of that name, then a default from the folder (`detect_pm`: pnpm-lock, yarn.lock, package-lock/package.json, uv.lock/pyproject, requirements.txt, Cargo.toml).
- **update** (`verb_update`): refuses on uncommitted tracked changes; fetch, default branch, `pull --ff-only`; measures changes from the commit hyperbeam last updated or installed (`<project data>/updated-commit`, written after a successful update or install; else Merge's `since`, else the HEAD before the pull), so a manual pull by someone else still counts; if the project has its own `update` (manifest `[commands]`, package.json script, Makefile target) runs it whenever any file changed (failure: says so, exit 1), else runs `install` only if a lockfile changed; restarts the service windows (`C-c`, then the manifest command) if the session runs. For hyperbeam it runs `hyperbeam update --yes`. **test** always goes through `lab run --why "NAME test"`. **version**: package version + `git describe` + last commit date. **help**: each verb and where it comes from.
- **Sidebar:** Update (u) runs the selected project's `update` (hyperbeam's row: a tmux popup, because the update restarts the menu); More has Install, Test, Version, Help. Output: the last line in the notice, all of it in `<project data>/verb-<verb>.txt`. **A successful Merge runs `update` by itself** (and writes `merge-verified`, which `hyperbeam verify` looks for).
- **In a session:** `NAME VERB` and `hb VERB` do the same (`~/.local/share/hyperbeam/bin` is first on the session PATH: `hb` acts on `$HB_PROJECT`, plus one shim per project; no shim where a real command of that name exists or for reserved names).
- **`hyperbeam new NAME [--cli|--web] [--about "..."] [--no-open]`** creates `~/projects/NAME` that already conforms: git, README, CLAUDE.md (imports `@.hyperbeam/RULES.md`), docs/DECISIONS.md, an entry point answering the verbs (a Python+uv CLI with tests, or a Node web app with `--version`, `/version` and `node --test`), the manifest (committed straight to hyperbeam's main; a free port from 3100) and a first commit, then Open.
- ALIGN.md proposes the smallest real addition where a project only has hyperbeam's default.

## The sidebar and the menu
- **Menu** (`Menu`, Textual, no tabs): a row is a dot (running projects only), the name, the branch (only when not main/master; light pink with an open PR) and the port (`-` manifest without a port, orange `unset` no manifest); the dot and port are never cut, the branch shrinks first (down to 6 characters), then the name. Name bold white when opened within `recent_days`, else grey. Order: manager row, running, recent, the rest. The hyperbeam row shows `branch` (checkout not on main) or `behind` (origin/main is ahead, fetched every 10 min) in yellow. A `»` after the dot marks a running worker. Under the list: the selected project's dot reason.
- **Buttons:** Open (o), Stop (s), Done (d), Update (u), **Merge** (m, full width, only with an open PR), More (j: the Project screen), Hide (h, sidebar only). Hidden keys: `i`/`j` Project, `t` Settings, `c` copy context, `p` copy last, `r` refresh, `q` quit. Single click selects, double click or Enter opens (the handler must `prevent_default()`). Textual reads `[x]` as markup: write `Open (o)`.
- **Title line:** `5h 83% - resets Thu 1:00am`, or `update available (u)` while origin/main is ahead.
- **Dots:** green running, blue Claude waits for you, cyan working; priority red > blue > cyan > green. **Red is rare:** (1) a service down or failed its ready check, (2) obvious secrets in commits on no remote (`commit_secrets`, file/line/pattern only), (3) a merge/rebase/cherry-pick/revert stuck with conflicts. Everything else (uncommitted, unpushed, stash, behind, detached HEAD, a crash, drift, stale docs, a huge conversation) is a quiet note: in `kk`, the session's yellow status segment and the Project screen, never the dot. Red and notes are in `<project data>/status.json` (written on Open, redone by Refresh and every minute, cleared on Stop). The session status line shows a red `⚠ problem (+N): kk` or a yellow `note: ...` (`tag_session`, `sync_alert`; `hyperbeam _entered` refreshes it when a client enters). In tmux commands use the plain session name, not `=name`, with `set-option`/`show-options`.
- **Polling:** sessions every 3 s, status 5 s, PR list 60 s (cache read from disk every 5 s), notes recheck every minute.
- **Project screen** (`ProjectScreen`, a modal): path, branch, port, services, PRs, red problems, notes, onboarded date and drift, the verbs line (`own: ...; hyperbeam's: ...`), conversation size and both usage limits. Buttons: Update, Install, Test (lab), Version, Help, Edit manifest (opens `projects/<name>.toml` in a `manifest` window of the session), Copy context, Copy last, Info window (the `kk` text in a tmux window), Mark onboarded (takes the drift baseline), Settings, Keys, Hide. A button closes the screen and the Menu runs the action.
- **Settings (t)** is a modal that owns all input (Up/Down rows, Left/Right or Enter and −/+ change, Esc closes); then the key sheet (`KEYS`/`HINT`, kept in step with hyperbeam.conf). Never `return self.dismiss()` from a handler (`ScreenError`): call it, then return. Confirm and Choice are modals that stop their button events.
- **Sidebar window** (desktop): one kitty OS window with two splits: the menu on the left (outside tmux, so Textual's mouse works), `hyperbeam _right` on the right (a tmux client on `=manager`). Open switches that client (`sidebar_client()` = the tty `_right` recorded in `sidebar.json`; no guessing). Launch (`launch_sidebar`) writes `sidebar.session` (it must not start with `new_os_window`) and runs `kitty --class hyperbeam-sidebar --title hyperbeam --session FILE -o allow_remote_control=socket-only --listen-on unix:$XDG_RUNTIME_DIR/hyperbeam-sidebar -o enabled_layouts=splits,stack`. The menu sets its own width with `kitten @ resize-window` (`fit_width`, on start, on a `menu_width` change and on resize). **Hide/show** (`M-s`, `hyperbeam sidebar`, Hide): `goto-layout stack` / `splits`; nothing is closed. A half-open window (one half missing) is closed and reopened by the hotkey; a whole one answers "already open". The menu loop restarts after any exit but `q` (code 0). Stopping a project first moves its clients to `manager:home`, so the right split never closes (and `show_session` reopens it if it is gone). Not used over SSH, inside tmux or without a screen: `hyperbeam` attaches instead. Done in the sidebar closes the window (`_close-sidebar`); the tmux sessions are not touched.
- **The manager session** has windows `home` (the manager's Claude left, a shell right) and `menu` (the menu alone, for SSH/phone). The sidebar's right client sees `home`, every other client `menu` (`home_target`).
- **Modes (`open_mode`):** `sidebar` (above), `switch` (the client looking at the menu switches), `window` (a new kitty per project; over SSH it switches). Local or remote is the client's (`client_pid`: its environment has SSH_CONNECTION/SSH_TTY or an ancestor is sshd, mosh-server or tailscaled).

## Sessions: Open, layouts, start check, Stop, Done
- **Open** attaches if the session runs. Otherwise `open_project`: link `.hyperbeam`; `start_check` (findings and notes only); `start_session`: tmux session `<name>` with `HB_PROJECT`, `HB_STATE`, `PORT`/`HB_PORT` (if set), `HOST=0.0.0.0` and the manifest's `[env]`; window `work` (Claude 60% left, shell 40% right), one window per service started in order (its output is the log); a service starts after the previous one is ready; then the shell prints warnings and runs `kk` and Claude starts: `claude --continue ... || claude ...` (`claude_cmd`), always plain, nothing injected, nothing asked. A failing service or a missing manifest does not stop the session: the dot goes red and `<project data>/notes/YYYY-MM-DD-services.md` has the result and the window's last lines. Splits are percentages, so they scale to other clients.
- **Layouts** (`<project data>/layout.json`): per window its name and `#{window_layout}`, per pane its cwd, role (`claude`, `shell`, `service:<name>`, `other`) and for `other` the program running in it; the active window and pane, a time and `clean`. Saved on Stop (`clean: true`), by the tmux hooks `client-detached` and `client-session-changed` (`hyperbeam _save`), every 5 minutes while the menu runs, and when a session starts. Open on a stopped project with a layout restores it without asking: windows, panes, cwds; services restart from the manifest; Claude panes run `claude --continue` (first per directory); a program pane gets its command typed again (`restart_programs`; not a shell, Claude, `sudo` or tmux). The manager session is saved too (`home`; `menu` is rebuilt) and rebuilt after a reboot (`ensure_menu`). `select-layout` is ignored when the pane count differs, so panes are made first.
- **Start check** (`start_check`, `hyperbeam _check PATH [--fetch]`): uncommitted changes, unpushed commits, stashes, detached HEAD, a merge/rebase/cherry-pick/revert in progress, behind upstream (after a `git fetch` limited to 6 s), "not stopped cleanly" (a layout with `clean: false` and no session); steno files left out. Only red findings count as problems; the rest are notes. Printed in the shell pane and shown in `kk`; nothing is sent to Claude.
- **Stop** (s, `hyperbeam stop`): runs the wrap-up check first. Clean: confirm, run each service's `stop` in reverse order, kill the session, check the ports closed. Not clean: the menu offers Stop anyway or Cancel; the CLI prints the findings and refuses without `--force`. Refuses to stop the manager session. Without a manifest it only kills the session.
- **Session record** `journal.json`: `started`, `menu_started`, the projects opened or switched to (`touch_opened`, `_save`); survives a menu restart, cleared by a completed Done.
- **Wrap-up check** (`wrapup_check`, `hyperbeam _wrapup PATH [--since TS]`): uncommitted/unpushed work, stashes, detached HEAD, merge/rebase; steno files tracked or not ignored; obvious secrets in commits since the record started, staged and unstaged changes, untracked files, and secret-looking file names (`.env`, `id_*`, `*.pem`, `*.key`, `credentials.*`). Patterns: private-key headers, AWS/GitHub/Slack/Stripe/Google/Anthropic/OpenAI keys, URLs with a password (not localhost), literal password/secret/token assignments (not in test/fixture dirs). Output is file, line, pattern, never a value. A check that finds something is written to `<project data>/notes/YYYY-MM-DD-wrapup.md` before the user chooses.
- **Done (d)** runs the wrap-up check on every project worked on since the menu started. All clean: confirm, stop their sessions (never one whose Claude is working or waiting; those are named and left, and the record and the window stay), close the window, clear the record. Otherwise it lists what is unclean and stops nothing. No offers follow; the manager does that work.
- **`HB_CLAUDE_PANE`:** every session has the tmux pane id of its Claude pane (`publish_claude_pane` at creation and after a restore; `refresh_claude_pane` re-derives it from `_save` and `update`). Tools in the session (stenographr) use `tmux send-keys -t "$HB_CLAUDE_PANE" -l "text"` and never guess the pane.
- **Injecting a prompt** (`inject_prompt`, used only for the Merge "update and re-test" request): into the Claude pane as `Read FILE and follow it.`, else `claude --continue "$(cat FILE)" || claude ...`; never into the menu pane (`find_claude_pane`).

## Claude's state, hooks and tmux keys
- **Hooks** (`hyperbeam _hooks`, run by `update`) merge into `~/.claude/settings.json` (one backup `settings.json.hyperbeam-backup`, idempotent, nothing else touched): state hooks write `$HB_STATE/claude`: `waiting <reason>` on `Stop`, `Notification` and `PreToolUse` for `AskUserQuestion|ExitPlanMode`; `working` on `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure` and `PermissionDenied` (a prompt Claude blocked by itself); an `idle_prompt` Notification leaves `finished` alone. The state is ignored unless a process named `claude` runs in the project's Claude pane. Also: the guard (`PreToolUse` on Bash), the PR refresh hook (`hooks/pr-refresh.sh`, `PostToolUse` after `gh pr create|merge|close`), the worker report (`Stop` with `HB_WORKER=1`), and a snippet in the status line script that writes `rate-limits.json`. Claude reads hooks at start: a running Claude needs a restart after they change. `"model": "opusplan"` in settings is changed to `"sonnet"` once.
- **Keys** (hyperbeam.conf, no prefix; sessions hyperbeam creates carry the tmux option `@hb`): `M-h` back to the manager session, `M-]` / `M-[` next / previous in the stack (the manager, then `@hb` sessions by creation time; per client), `M-s` hide/show the sidebar, `M-y` copy, `M-Left/Right/Up/Down` select pane, `M-z` zoom. Mouse on: dragging copies to the tmux buffer and, locally, the Wayland clipboard. Shift+Tab is Claude's plan mode. Alt+arrow word jumps in Claude's prompt do not work (tmux takes them); Alt+b/f do.
- **`M-y`** copies the current pane. In a Claude pane it is the whole conversation from Claude Code's own session file (`~/.claude/projects/<cwd, non-alphanumerics as "-">/<id>.jsonl`, found through `~/.claude/sessions/<pid>.json`): `### You` / `### Claude` blocks, tool calls as `  [Bash] <command>`, no thinking, tool output or sidechains. In any other pane the scrollback (`history-limit` 50000). Local: `wl-copy` (run from the tmux server, with a fallback to the socket in `$XDG_RUNTIME_DIR`); remote: `outbox/<session>-<time>.txt`. `HB_CLAUDE_DIR` overrides `~/.claude` in tests.
- **Copy last** (`hyperbeam copy-last`, button/`p`): Claude's final text answer in the turn of the user's last real prompt, read from the conversation file (`last_assistant_message`; `is_human_prompt` skips task notifications, auto-continuations, meta records, tool results and sidechains; a short answer to a leftover notification is skipped). Delivered like Copy context (`deliver_text`), then its first line so the user can see it is the right one.

## Pull requests and Merge
- **PR badge:** for projects whose origin is on GitHub (`github_slug`: github.com or a `github-<account>` alias) `open_prs` lists your open PRs (`gh pr list --author @me`), cached in `<project data>/prs.json` for 5 minutes. Each call uses the token of the gh account named like the repo's owner (`gh auth token --user OWNER`, only in that call's environment); an owner without a login gets no badge and Merge says `no gh login for OWNER (run: gh auth login)`. Branch text turns magenta; the detail line shows `PR #N: title`; a PR older than 7 days is marked `[stale: Nd]`.
- **`hyperbeam refresh-prs [PROJECT] [NUMBER...] [--gone N...]`** fetches now (new numbers by `gh pr view`, because the list lags), writes the cache and signals the menus (SIGUSR2). Nothing has to remember it: a PostToolUse hook runs it in the background after `gh pr create|merge|close`.
- **Merge (m)**, only with an open PR: all your open PRs of the project, oldest first, after one confirmation (`_merge_all`). Before each, `pr_state` fetches the branch and base and returns how far behind it is, the files main changed that the PR also changed (`overlap`) and the files a `git merge-tree` dry run would conflict in; `None` (offline, a fork) is said out loud and merges unchecked. **No overlap:** merged without a question. **Overlap:** a modal: *Ask Claude to update and re-test* (default; hyperbeam types text into the project's Claude only because the user clicked this button: `update_prompt` injected: rebase, re-run in the lab, push, don't merge), *Merge anyway*, Cancel. **Conflict:** no merge anyway; Claude is asked to rebase and the run stops. The first PR that needs a look stops the run ("merged #33; stopped at #34: ..."). Each merge is `gh pr merge N --merge --delete-branch` (retried once on "Base branch was modified"); the local checkout is then pulled `--ff-only` only if it is on the default or the merged branch and clean, and the merged local branch deleted; a feature branch in progress is left alone. **After the last merge the project's `update` runs once** (`verb_update(since=)`: installs if a lockfile changed, restarts services only if something changed). The merged PRs are dropped from the list at once. The run ends there; the manager plans what comes next.

## Workers
- `hyperbeam work NAME FILE`: makes sure the user's session `NAME` runs (detached, with services; start-check problems go to the top of the worker's prompt), then starts tmux session `claude-NAME` (no services of its own) in the project's folder: one window, `claude_base()` (configured model, effort, permissions; never plan mode) with WORKER.md + the file as its first message, fresh. Environment: the session's, plus `HB_WORKER=1`, `HB_REPORTS` (`<project data>/reports/`) and `HB_STATE` = `<project data>/worker` (its own state, so the user's dot is unchanged). The worker works and commits in a git worktree (WORKER.md). Refuses if `claude-NAME` exists: one worker per project. Before any Claude starts there (`work`, `start_session`, `hyperbeam new`) `trust_folder` sets `projects[<path>].hasTrustDialogAccepted` in `$CLAUDE_CONFIG_DIR/.claude.json` (default `~/.claude.json`; workers use the same file) unless it is already true, so a new project's first Claude does not stop at the trust dialog; only that key, temp file + rename, skipped quietly on any error.
- `wait NAME... [--timeout S]` blocks until each worker's Stop and prints each report path (exit 1 on timeout, 2 if a worker asks a question, has sat at a permission prompt for 3 minutes (Claude Code blocks it by itself after ~2 and carries on) or its session ended). `send NAME FILE|-` pastes the file (or stdin) into a finished worker's Claude as one bracketed paste + Enter (review feedback); it refuses while the worker works or sits at a prompt. The report lists commits on the branches the worker created or moved (the refs at start, in `started.json`, against now: a worker in a git worktree commits on a branch the project folder isn't on, and others' merges are not listed). `close NAME` kills `claude-NAME` (only with `HB_WORKER=1`), never the user's session, then quietly removes that project's clean worktrees under ~/.cache/hyperbeam-work whose branch is merged. `tidy [NAME]` lists, and with `--yes` deletes, per project: local branches and `origin` branches merged into origin/main, those worktrees, and (without NAME) empty dirs there; it skips and says why for a dirty worktree, an unmerged, checked-out or other-worktree branch (`git branch -d`, `git push origin --delete`, `git worktree remove` without --force; squash merges are not detected). `status` lists sessions and worker states.
- **Report:** at Stop with `HB_WORKER=1` the hook runs `hyperbeam _worker-report`, writing `reports/<date-time with seconds>-<slug>.md`: the task's first line, start and finish, Claude's final message, branch, commits, the PR URL, the transcript path. One report per worker run (the name is kept in `started.json`): a later Stop rewrites it; after a `send` the previous final message moves to an "Earlier rounds" section.
- **Onboarding and aligning** are worker tasks the manager sends after a yes: `ONBOARDING.md` (read the project, start and test it, write and commit `projects/<name>.toml`) and `ALIGN.md` (compare with RULES.md using `align-facts`, propose, wait for approval in the conversation, then a branch and a PR). The Docker rule: dev servers run on the host in a tmux window; backing services (databases, Supabase, Caddy) run through docker compose.

## Checks that cost no tokens
- **Drift:** `fingerprint(path)` = the run-defining parts of `package.json` (scripts, dependency names, workspaces), compose files (services, images, ports), `pyproject.toml`, `requirements*.txt`, `Procfile`, Makefile targets, `.env.example` names, `Cargo.toml`; versions and lockfiles are noise. Stored with a date in `fingerprint.json` when a manifest was written, on Mark onboarded, or as a silent baseline the first time a project with a manifest is checked. `drift_notes` (on Open, Refresh, the minute check) says `setup changed since onboarding: <file> (<parts>)`.
- **Stale docs** (`stale_doc_items`): in README.md and CLAUDE.md, (1) `npm|pnpm|yarn|bun run X` / `make X` commands that are no package.json script or Makefile target, (2) backticked relative paths that are not tracked or on disk, (3) a doc last committed 5 or more commits (`STALE_AGE_COMMITS`) that touched run-defining files ago. One quiet note `docs may be stale: ... (send ALIGN.md as a worker task)`.
- **Usage** (`hyperbeam usage`): the 5-hour limit is shared with claude.ai, so it is not estimated: Claude Code's status line gets `rate_limits.five_hour` and `seven_day`, and the hyperbeam snippet in `~/.claude/statusline-command.sh` writes them to `rate-limits.json` (older than 5 minutes shows `(as of 9:41pm)`). Local numbers (requests and tokens per project, `conversation_sizes`) are labelled Claude Code only.
- **Context note:** a running project whose conversation was active in the last 3 hours and re-reads at least `context_warn` tokens per request gets a quiet note to finish the task and start a fresh Claude (Copy context carries what matters).

## Lab
- **Why and what:** agents testing on the user's machine kept breaking live work. The lab is a user `hblab` (a different uid: nothing it runs can signal the user's processes) whose home `/srv/hblab` is a fixed-size ext4 image (`/var/lib/hyperbeam-lab.img`, mounted by fstab). The user's `sudo bash lab/setup.sh [SIZE]` creates it (`remove.sh` undoes it, `podman-setup.sh` adds rootless podman); the sudoers rule `<user> ALL=(hblab) NOPASSWD: ALL` allows commands as hblab only. Agents never run these and never suggest rerunning, undoing or resizing the lab because of an error. Until set up, every `lab` command says so and exits 2 (`lab_ready`).
- **`hyperbeam lab run [--dir DIR] [--name N] [--why TEXT] [--fresh] [--collect PATH] [--timeout S] [--] COMMAND...`** (options before the command; a misplaced `--why` is an error): one synced copy per project in `/srv/hblab/projects/<name>` by `rsync -a --delete` as hblab (`lab/sudo-hblab` is rsync's remote shell). Not synced: `.git`, `node_modules`, `.venv`, `venv`, `__pycache__`, `.next`, `target`, `.pytest_cache`, `.hyperbeam`; never copied: `steno-*.txt`, `.env`, `.env.*` (not `.env.example`), `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*`. Installs persist, so only the first run is slow; `--fresh` wipes the copy. The command runs as hblab under `env -i` with its own `TMUX_TMPDIR`, `XDG_RUNTIME_DIR`, `DISPLAY=:99` (Xvfb), no `WAYLAND_DISPLAY`, `HB_LAB=1`, `LAB_PORT_MIN`/`LAB_PORT_MAX` and the package caches under `/srv/hblab/cache`. One argument is a shell command line, several are argv. `--timeout` defaults to 600 s (`timeout -k 5`). `--collect PATH` rsyncs a file or folder from the lab copy back to `~/.cache/hyperbeam-shots/<time>/`.
- **Ports and Docker:** the lab shares the machine's network: bind port 0 or 39000-39999, never a project's 3100+. Docker is not in the lab (the docker group is root); Docker-based tests are a listed exception in the project's CLAUDE.md. `lab run` writes `podman` and `docker` shims for hblab (single containers and host-network compose work; `docs/PODMAN.md`). pnpm is installed by npm into `/srv/hblab/cache/tools` (corepack's shim does not work). hblab is in `video` and `render` for GPU access.
- **Isolation between runs:** each run has an 8-hex id, its own session (`setsid -w`), `TMUX_TMPDIR=/srv/hblab/tmux/<id>` and `XDG_RUNTIME_DIR=/srv/hblab/rt/<id>`, and is recorded in `/srv/hblab/runs/<id>.json`; everything it starts inherits `HB_RUN_ID`, which is how its processes are found and stopped when it ends. The display is shared infrastructure, never stopped by a run.
- **Nesting:** inside the lab (`HB_LAB=1`) any lab command (`lab`, `tool`, `shot`, `NAME test`) refuses itself with `LAB_NESTED` (the message says nothing needs changing). Don't wrap them in `lab run`.
- **Other commands:** `lab status` (disk, synced projects, caches, active runs, hblab's processes); `lab stop [PROJECT]` stops only that project's runs (SIGTERM, 3 s, SIGKILL); `lab reset [--all] [--force]` is the user's (it refuses while another project has a run; `--force` kills everything); `lab log [--today]` prints the run log; every run appends a line to `lab-runs.jsonl` (`time`, `project`, `cwd`, `command`, `why`, `seconds`, `exit`, `tail`).
- **Digest** (`lab digest [--today | --since YYYY-MM-DD] [--no-tests]`, no tokens): per project runs, time, failed and killed; **flaky** (failed then passed the same day); **where the time went** (top 5 commands by count x average); **tool candidates** (a command repeated 3+ times, or a 2-3 command sequence repeated 3+ times within a session, costing 30 s or more in total; commands are normalised by `norm_command`). Per tool: runs, failures and runs matching `tools/<name>/replaces` that did not use it.
- **Tools:** `tools/<name>/<name>` (Go built by `build_tool`, or bash/python3) with `tools/<name>/test` (exit 0 = pass); listed in TOOLS.md, which every agent checks first. `hyperbeam tool NAME [ARGS]` runs one in the lab (`--dir` picks the folder), `tool --list` prints TOOLS.md, `tool --test [NAME]` runs the tests. A tool with a `host` marker file (`tools/recall/host`) runs as the user instead (it reads the user's own data, which the lab user cannot); its test still runs in the lab. `recall` (Go, SQLite FTS5 in `~/.local/share/hyperbeam/recall.db`, env overrides `RECALL_DB`, `RECALL_CLAUDE`, `RECALL_STENO`, `RECALL_MANAGER`): `search`, `show`, `index`, `stats`. Every `lab run` syncs `tools/` to `/srv/hblab/tools` (`$HB_TOOLS`). Once a day, 20 s after the sidebar starts, `daily_tool_check` runs every tool's test; a failing tool is a quiet note on the hyperbeam row. `HB_TOOLS_SRC` points at another tools folder (tests).
- **`hyperbeam verify [github|hooks|lab|merge|all]`** (the user runs it; prints PASS/FAIL/YOU with the command to run): gh logins per owner, hooks and model in `~/.claude/settings.json`, the lab (ready, disk, hblab cannot read the home folder), podman, and the one thing only the user can test: a real Merge.
- **`hyperbeam shot [--cols 35] [--rows 40] [--phone] [--dir DIR] [--screen all|main|pr|project|settings|merge|done]`** runs `_shot-render` in the lab (throwaway projects, the menu in a pty read with pyte, each screen drawn to PNG with PIL) and collects the files into `~/.cache/hyperbeam-shots/<time>/`; Claude reads the PNGs. `--dir` draws a branch's checkout. `docs/UI.md` has the constraints.

## Guard (`guard.py`, PreToolUse on Bash)
- **Why:** agents inside a hyperbeam session have `$TMUX`, so a bare `tmux ...` reaches the user's real server; a `tmux kill-server` once took down every session, and CLAUDE.md text did not stop it.
- **Mechanism:** the hook gets `{"tool_name": "Bash", "tool_input": {"command": ...}}` on stdin; exit 2 with a message on stderr blocks and the message goes to Claude. The hook command exits 0 at once without `$HB_PROJECT`, else `/usr/bin/python3 <repo>/guard.py` (stdlib only). Installed by `hyperbeam _hooks` from the live checkout.
- **Rules** (`RULES`, one table; one tokenizer; quoted text is data, so a command that only mentions a blocked word inside quotes passes): tmux kill commands not aimed at another socket (`-L NAME` or `-S PATH` naming one that is not `$TMUX`'s); `kill`/`pkill`/`killall` outside `hyperbeam lab run` (any `pkill -f` pattern can match a tmux server's own command line); a GUI app with `WAYLAND_DISPLAY` or `DISPLAY` set unless the command unsets both; `lab reset`; `git worktree remove --force`; `rm -r` of a dirty worktree; the lab's setup scripts; any `sudo` but `sudo -n -l`; running a `hyperbeam` script from a worktree or the dev folder outside `hyperbeam lab run` (`lab run`, `tool`, `shot` and `lab status|stop|log|digest` are the exceptions). A block message says what to do instead. Nesting is the lab's business, not the guard's.
- Test a rule by feeding sample JSON to `guard.py`, never by running the command. hyperbeam's own tmux calls are not affected: hooks see only Claude's tool calls.

## Update and try
`hyperbeam update` (the Update button on the hyperbeam row): refuses on uncommitted tracked changes in ~/projects/hyperbeam; `git fetch`, check out `main`, fast-forward to `origin/main` (the installed copy is always on main), print `old -> new` and the new commits; then the new script's `_update-finish`: `_hooks`, reload hyperbeam.conf and the status hints, link `kk`, restart the menus (SIGUSR1 to the pids in `menus/`; they exit 75 and their loop restarts them), and offer to restart idle Claude panes with `claude --continue` (`--yes` skips the question; working ones are left alone). `try BRANCH` is the same with that branch; `update` returns to main. Tests use `HB_SETTINGS` and a scratch clone.

## Manifest format
`projects/<name>.toml` in this repo, never in the project; written by an ONBOARDING worker. `port` is optional (no port: no `PORT`/`HB_PORT`); ports start at 3100 and never repeat across manifests.

```toml
path = "~/projects/plantlab"
port = 3101

[[service]]                # ordered; each waits for the previous one to be ready
name = "db"                # tmux window name
cmd = "docker compose up"  # run in the project dir; sees $PORT and $HB_PORT
ready_port = 54322         # wait until this TCP port opens. Default: the project's port. false = don't wait
stop = "docker compose down"   # optional; Stop runs these in reverse order before killing the session

[[service]]
name = "dev"
cmd = "pnpm dev"           # ready_port defaults to port = 3101
ready_delay = 5            # optional: sleep N seconds first (alone, it replaces the port check)
ready_timeout = 60         # optional: give up waiting after N seconds (default 120)

[env]                      # optional: extra session env, overrides the defaults (HOST=0.0.0.0)
SOME_VAR = "value"

[commands]                 # optional: override a verb (install, update, test, version, help, restart)
test = "pnpm test"

[links]                    # optional: extras `kk` cannot discover; name = url
docs = "https://example.com/docs"
```
A service that exits before its port opens is a warning and the next one still starts.

**Over Tailscale** the phone reaches dev servers at `http://<MagicDNS name>:<port>` (from `tailscale status --json`; no tunnels). A server must bind all interfaces, which the manifest arranges, never the project: Next.js does by default; Vite needs `--host $HOST --port $HB_PORT` and `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS=.ts.net` in `[env]`; docker compose publishes on 0.0.0.0. ufw is off.

## Testing
`tests/test_worker_loop.py` runs the worker loop on a real, isolated tmux (`HB_TMUX_SOCKET=<name>` makes hyperbeam use `tmux -L <name>`) with a fake `claude`. All of it in the lab (`hyperbeam hyperbeam test`: `uv run --with textual python3 -m unittest discover -s tests`; tools have their own `tools/<name>/test`). Pattern: a throwaway set of projects and manifests (`HB_MANIFESTS`, `HB_CONFIG`, `XDG_DATA_HOME`), fake `claude`/`gh`/`wl-copy` on PATH, an isolated tmux (the lab gives it one), the menu driven through a pty read with pyte, never `tmux send-keys` (it bypasses the client). Never `pkill -f` a pattern in your own command line.
**Windows:** the rule (nothing opens on the user's screens; `WAYLAND_DISPLAY` and `DISPLAY` unset in every test run) is in CLAUDE.md; with `HB_CONFIG` set `spawn_kitty` refuses to open a window unless `HB_KITTY_ARGS` is set.

## Decision records
One file per decision, `docs/decisions/YYYY-MM-DD-slug.md`: front matter `id` (the file name), `status` (`implemented` | `superseded`), `topic`, `prs`, optionally `supersedes: [ids]`, `collapsed_into: [ids]`, `code: path:function`; then `# Title` and Decision / Why / Rejected. A decision that replaces earlier ones lists them in `supersedes`, and each of those becomes `status: superseded` with `collapsed_into` (a decision) and/or `code`. The implemented set is what is true now. `docs/DECISIONS.md` is generated (`hyperbeam tool decisions index > docs/DECISIONS.md`), only by a worker task from the manager, never by a feature PR. `hyperbeam tool decisions list [--topic T]|check|index` (Go, `tools/decisions/`; `check` verifies ids, status, targets, no cycles).

## Gotchas
- `supabase status` prints keys next to URLs: never print its raw output (`-o json`, URL values only).
- pnpm 12 installs by itself on `pnpm dev`: opening a project with no `node_modules` modifies it.
- `claude "prompt"` starts an interactive session with that prompt; `-c` continues, `-r` resumes, `-n` names.
